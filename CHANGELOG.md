# Changelog

Releases are recorded here. While the spec is a pre-1.0 draft, drafting churn lives in git history, not in version bumps — the version moves when there is a consumer-visible reason for it to move.

## Unreleased

- **`@issuegraph/cli`'s `order` and `ready` accept an OPAQUE tracker identifier, so a Jira or Linear corpus can be ordered at all.** **Closes [#33](https://github.com/autnmy/issuegraph/issues/33).** SPEC §4.2 defines a reference as an opaque tracker-scoped token ([#25](https://github.com/autnmy/issuegraph/pull/25)); the input document had not caught up, keying every issue by a numeric `number`, so `asInteger` refused the whole corpus at the boundary. Worse than unsupported: a body in such a corpus can carry a valid `blocked-by: ABC-123` that the reader resolves, and the caller had no way to supply the issue it targets.
  - **`id` is added; `number` is kept.** `number` is the published contract and every existing caller sends it. Supply one or the other — both is accepted **while they agree**, so migrating is not a flag day, and refused when they disagree, because one issue named two ways has no correct reading. Neither is refused as well: an issue with no identifier cannot be named by any body in the corpus.
  - **One referenceability predicate, over the string the reader stores.** `isReferenceableId` now takes the id rather than a number, because §4.2's widening makes the numeric spelling one CASE of the opaque one rather than the domain itself — so asking about a number and asking about an id is the same question. A second numeric predicate would be exactly the drifting restatement that function's own history warns about.
  - **The domain boundary now types the identifier as well as validating it.** `deriveOrder` is exported and a JavaScript caller reaches it with no compiler in the way, so the annotations promise nothing there. `id: 123` reached `resolveRef` and threw a `TypeError` instead of the usage result the function promises, and `id: null` with no `number` fell through to the key `"undefined"` and was **silently accepted** — an order keyed by a lie, which is the worse of the two. Raised in review.
  - **`@issuegraph/cli` 0.2.0** — a feature on a published `0.1.1`, and nothing depends on the CLI, so the minor bump strands no consumer.
  - **Both boundaries refuse, and each is pinned separately.** The JSON schema check (`asOrderInput`) and the domain check (`inputDomainRefusal`) are deliberately redundant, as they already are for duplicate keys — and testing only through `orderFromJson` cannot tell them apart, because it runs one and hands the result to the other, so deleting either still refuses. Verified by removing each and watching the suite stay green before the tests were written to hit them independently.

- **`@issuegraph/derive` 0.1.2 — a patch bump so [#50](https://github.com/autnmy/issuegraph/pull/50)'s path-compression fix can actually reach a consumer.** `derive@0.1.1` is published with the quadratic `find`, and `pnpm check:publishable` reports the package **STALE**: a release would skip it at exit 0 and the fix would never ship. That is the same silent-skip shape as [#36](https://github.com/autnmy/issuegraph/issues/36), caught this time by the guard that issue produced.
  - **PATCH, so no published consumer is republished to receive it.** A caret on a `0.x` version pins the MINOR, so `cli@0.1.1`'s `^0.1.0` on derive already admits `0.1.2`. A minor bump would strand it instead — the distinction #36 was about.
  - **Nothing else is stale.** The guard reports the other six packages byte-identical to what the registry holds, and no published consumer stranded.

- **`@issuegraph/reader` 0.2.1 and `@issuegraph/derive` 0.1.1 — patch bumps so [#46](https://github.com/autnmy/issuegraph/pull/46)'s fix can actually reach a consumer.** That PR taught the reader and the derivation to detect a `blocked-by` cycle running through a `together-with` unit, and changed no version. `pnpm publish --recursive` publishes only versions the registry does not already hold, so the next release would have **skipped both silently, at exit 0** — #36's failure mode exactly, and `pnpm check:publishable` reported both STALE for that reason. A consumer-visible fix is precisely the case this file's release discipline says the version moves for.
  - **PATCH, so no published consumer is republished to receive it.** A caret on a `0.x` version pins the MINOR, so the already-published `cli@0.1.1` — which carries `reader@^0.2.0` and `derive@^0.1.0` — resolves `0.2.1` and `0.1.1` without being touched. `check:publishable` confirms it: 0 published consumers stranded.
  - **`@issuegraph/viewer@0.1.0` publishes for the first time in this release.** It was blocked behind the two stale packages rather than by anything of its own — the publish workflow runs `check:publishable` before the irreversible step, and that gate is repo-wide, so one unbumped package holds up every other.

- **`buildTogetherComponents`' union-find compresses paths, so an ascending `together-with` chain is linear rather than quadratic.** **Closes [#48](https://github.com/autnmy/issuegraph/issues/48).** **`derive@0.1.1` shipped the quadratic version**, so this needs a further patch release to reach consumers — it is a fix to published code, not a fix ahead of one. That was nearly the opposite: `buildTogetherComponents` did not exist in `0.1.0`, so while this was being written there was no exposure at all, and the release above went out in the interval. The exposure is real but narrow — see the shape below.
  - **The reference DIRECTION decides the tree shape, which is why this was easy to miss.** The union attaches `find(key)` under `find(target)`, so `#2 together-with #1` (descending) hangs each new key off the existing root — a flat star, O(1) finds, fine at any size — while `#1 together-with #2` (ascending) makes each previous root a child of a brand-new node, giving a linked list the members loop then walks once per key. Measured at n = 20,000: **4.9 ms descending, 3,947 ms ascending**; 4.4 ms after the fix.
  - **The regression test is written in the ascending direction specifically, and that was verified rather than assumed** — the same test written descending passes against the unfixed code, which was confirmed by running it that way. Its budget is self-calibrating (the descending chain measures the machine, the ascending one has to stay within reach of it) because an absolute millisecond threshold is a promise about the hardware rather than about the code.
  - **A stray `|||||||` conflict marker is removed from this file.** [#46](https://github.com/autnmy/issuegraph/pull/46)'s changelog resolution was scripted against two-way conflict markers while git had produced **diff3** ones, so the base-section marker line survived into `main`. No content was lost or duplicated — it is one stray line — and it is swept here because this change had to resolve the same file anyway.
  - **Not shared with `@issuegraph/reader`'s `UnionFind`**, which is private to its model and already does exactly this. Exporting it would put a generic data structure into a published API surface under semver, for an algorithm that cannot semantically drift — unlike `canonicalOf` and `togetherComponent`, which are parameters precisely because they encode §4.3.3 and §4.3.7 and would drift if restated. A rule is worth sharing; a union-find is worth fifteen lines.

- **A selection is canonicalized in the SELECTION PATH, so every entry point agrees with the click it is documented to be equivalent to.** A `together-with` unit is one station in the linear and graph projections and its partners get no row of their own — so `navigable` does not hold them, and a selection of one was a subject focus could not follow: `resolveFocusKey` found it in no order and fell to the FIRST entry. Measured on the fixture, where slot `103` has member `104`: `handle.select('104')` in graph gave `{ selected: '104', focused: '102' }` — an unrelated issue — and the same state arrived by selecting `104` in the tree and switching to graph. **Closes [#45](https://github.com/autnmy/issuegraph/issues/45).**
  - **The previous fix was in the MARKUP, which is why two doors stayed open.** [#24](https://github.com/autnmy/issuegraph/pull/24)'s last round routed a member's canvas node to its lead through `GROUP_ATTRIBUTE`, closing the pointer path — and `handle.select` and `setProjection` never touch the DOM, so neither could see the rule. `Scene` now publishes `stationOf` (key → the key that represents it here) and `reconcile` maps the selection through it, which is the one place all four doors pass.
  - **The tree publishes an EMPTY station map, deliberately.** It draws every key its own row, so a partner there is its own subject; canonicalizing would jump the reader to a row they did not click. The rule is projection-dependent, which is exactly why it could not live in `emitSelect`.
  - **This is not a drop, and `reconcile`'s promise is unchanged.** A switch changes representation, never subject — the unit IS the subject and the lead is this projection's name for it. A key nothing represents is still carried whole with focus falling back, and that half has its own test.
  - **A reconciliation that renames the selection now notifies.** `draw` announced only the document-membership DROP, so `setProjection` renamed the selection and told nobody: the handle read the station while the host still held the member. Found by the new invariant test rather than reasoned about.
  - **The canonicalization runs BEFORE the scene is built, not only after it.** Reconciling afterwards fixed the state a handle reports and left the MARKUP built from the un-canonicalized key: measured, `handle.select('104')` reported `selected: '103'` while **nothing** in the DOM carried `aria-current` and the roving tab stop sat on `102`. `renderViewer` was simply wrong, because it never calls `reconcile` at all. Each projection now names the caller's `selected`/`focused` its own way at the top of the function and publishes the same map it used, so the markup and `reconcile` cannot reach different answers. That also closes a fourth door — mount options carrying a partner as the initial selection.
  - **The guard is the invariant, not the case.** Three rounds found this class through three doors — a pointer, `handle.select`, a projection switch — each time because the test named the door. `mount.test.ts` now asserts, over every entry point and all three projections, that `state.selected` is either null or a key the ACTIVE projection publishes in `navigable`, that focus is on it, that `onSelect` reported the same key the handle holds, **and that the DOM marks exactly that key `aria-current` and gives exactly it the tab stop**. Checking only the state is what let the markup half through.
  - **One test asserted the defect and was corrected.** `keeps a selection the new projection does not draw` pinned `selected: '104'` with `focused: '102'` and called that focus "falling back to something reachable". It is a state no keyboard and no click can produce.
  - **`Scene` gains a required `stationOf`** — breaking for anything implementing a projection outside this package.

- **A `blocked-by` cycle running through a `together-with` unit is now detected — it was a permanent deadlock that nothing reported.** `#1 blocked-by #2`, `#3 blocked-by #1`, `#2 together-with #3` can never start: #2 waits on its unit partner #3, #3 waits on #1, #1 waits on #2. Before this, `Model.cycles` was empty, `diagnostics` was empty, and all three readiness sentences named an ordinary open blocker — the deadlock had **no surface at all**. **Closes [#43](https://github.com/autnmy/issuegraph/issues/43).**
  - **The cause is one line of graph shape: the vertex was the issue, and it has to be the unit.** §4.3.7 makes a together group one schedulable unit, so a blocker on any member blocks every member; readiness already reads the graph that way, and cycle detection did not. Both sites now contract the group to a single vertex before searching — `Model.cycles` (Tarjan over units) and `wouldCycleOnBlockedBy` (the pre-write guard).
  - **SPEC §6.6 says so now, rather than leaving it to be inferred.** The section defined a stuck group as an SCC of the open `blocked-by` graph and never said what a unit does to that graph. It now states the contraction, the boundary-crossing-edges-only rule, that a stuck group is reported as issue keys, and that a reader which does not contract is not conforming.
  - **Internal edges stay advisory, and a self-loop still reports.** §4.3.7 says a member-blocking-member edge is not a readiness input — it "would deadlock the group against itself" — so the contraction drops it, or every unit carrying its own ordering would read as stuck. The drop is conditioned on the EDGE (`b !== member`), which is the same test readiness applies at `b !== k`: an issue blocking ITSELF is not advisory ordering between two members, and both the singleton case and a self-loop on a member of a multi-issue unit fall out of that one condition. Both directions are pinned.
  - **The guard does NOT exempt internal edges, deliberately.** It already refused a circular internal pair before it understood units at all, so exempting them would *remove* a refusal — and every other divergence in that file points toward refusing more. §4.3.7 calls circular internal ordering a smell for grooming; refusing it at the write is the recoverable direction.
  - **`wouldCycleOnAdjacency` takes a required `togetherOf` resolver** — the same shape, and the same reasoning, as the existing `canonicalOf`: a default would be a second component walk, and an optional one would let a call site silently restore the un-contracted walk. Breaking for direct callers of that export; `wouldCycleOnBlockedBy` and `deriveIssueOrder` are unchanged at their own signatures.
  - **The pre-write guard builds its OWN together components, spanning closed nodes.** `Model.togetherComponent` unions only open endpoints — correctly, because "a closed member has left the unit" is true of readiness today — so a unit with a closed member is invisible to it. The guard is asked about the future: with `#1 blocked-by #2` and a **closed** `#2 together-with #3`, it admitted `#3 blocked-by #1`, and reopening `#2` then produced the permanent cycle it exists to refuse, with the edge already written. `buildTogetherComponents` walks the raw declarations, the same shape `buildBlockedByAdjacency` already uses for the other edge kind and for the same reason — divergence 1 applied to the other axis.
  - **The demo found it, and its known-gap pin is now an assertion.** [#9](https://github.com/autnmy/issuegraph/pull/9) replaced the demo's hand-rolled deriver — which *did* contract — with `@issuegraph/derive`, and rather than keep a second reading of the rules the demo pinned the difference as a failing-when-fixed test. It fired on this change, exactly as its comment said it would.

- **`@issuegraph/core` 0.1.1 — republished, because the published `0.1.0` cannot satisfy the consumers that depend on it.** `core@0.1.0` predates `isRefId` and `isRepoQualifier`, which [#25](https://github.com/autnmy/issuegraph/pull/25) added without moving the version. `pnpm publish --recursive` publishes only versions the registry does not already hold, so the next release **skipped `core` silently, at exit 0**, and published `@issuegraph/reader@0.2.0` and `@issuegraph/writer@0.1.0` — both of which import those two names, and both of which pnpm had rewritten to depend on `core@^0.1.0`, the stale tarball. Every fresh `npm install @issuegraph/cli` then threw on import: the binary exited 1 on every invocation and `import('@issuegraph/cli')` failed identically. **Closes [#36](https://github.com/autnmy/issuegraph/issues/36).** No source changed; this is a publish, not a fix.
  - **A PATCH bump, and the distinction is the whole repair rather than a style choice.** Every already-published consumer pins `core@^0.1.0`, and a caret on a `0.x` version pins the MINOR — so `^0.1.0` admits `0.1.1` and does **not** admit `0.2.0`. Publishing `0.1.1` repairs `reader@0.2.0`, `writer@0.1.0`, `derive@0.1.0` and `cli@0.1.0` **without republishing any of them**. Publishing `0.2.0` — the version "it adds exports, so it is a minor" argues for — would have left every one of them resolving the old `core` and reproduced the bug while looking like its fix. Measured end to end: the broken graph exits 1, and overlaying `core@0.1.1` alone takes `issuegraph parse` to exit 0 on a body with no block.
  - **The change is additive only.** `core` gains `SYMMETRIC_EDGE_FIELDS`, `isRefId`, `isRepoQualifier` and `isSymmetricEdgeField`; nothing was removed, renamed or revalued, so a consumer already resolving `0.1.0` cannot be broken by resolving `0.1.1` instead.

- **A guard that compares what a release would publish against what the registry already holds (`pnpm check:publishable`).** The reason #36 reached the registry unnoticed is that nothing asked this question. `ci.yml` builds and tests the workspace, where `workspace:^` always resolves to the local `core` — the one configuration that cannot fail — and `smoke-consumer.mjs` loads `dist` through that same link. Both are green in precisely the arrangement no consumer is ever in. It runs as the last gate before the irreversible step in `publish.yml` — on dry runs too, so a release can be rehearsed to find out what needs bumping. Deliberately **not** a per-PR job: this file's own release discipline says drafting churn lives in git history rather than in version bumps, so between releases a package's content is *expected* to have drifted from its published version, and a per-PR gate would red every pull request that edits package source. Its decision logic is still covered on every PR by `scripts/check-publishable.test.ts`.
  - **It asks two questions, and the second exists because the first opens a hole.** *Staleness*: did a package's authored content change while its version did not? That is #36, and a bump is the answer. Ranges the SOURCE manifest declares through the `workspace:` protocol are excluded from that comparison because pnpm derives them at pack time — bumping `core` alone rewrote the manifest of all four packages that depend on it, at nothing but `^0.1.0` → `^0.1.1`, and blocking a release on that is a false positive on a correct tree. *Resolvability* closes what the exclusion loses: a published consumer that is not being republished keeps the range it already carries, so the guard asks whether that range still admits the version this release uploads. Both are proven to fire — reverting the bump reports `core` STALE, and setting it to `0.2.0` reports all four consumers STRANDED. The blanking is narrow in both directions: it keeps the authored OPERATOR and drops only the derived version, so tightening `workspace:^` to `workspace:~` without a bump is still reported; and it keys on the DECLARATION rather than the package name, so a literal `"@issuegraph/core": "^0.1.0"` changed to `^0.2.0` without a bump is reported too. pnpm rewrites `workspace:` at pack time, so only the source manifest can say which ranges were derived.
  - **The control the issue prescribed was measured and does not work.** Packing every package, installing the tarballs into a scratch directory and importing them passes on the broken tree: the locally packed `core` satisfies the rewritten `^0.1.0`, so the stale published tarball is never fetched. A control that passes on the defect it was added for is decoration, and it is recorded here so it is not proposed again.
  - **An unreachable registry is `unknown`, never `new`.** Reading a transport failure as "not published" would wave through exactly the change the guard exists to stop, at the moment the network is the reason nobody can see the conflict. It fails closed and names the package it could not resolve. The range predicate is likewise an allowlist of two shapes — an exact version and a caret — returning `undefined` for anything else rather than guessing, because a wrong *admits* is the answer that ships the bug.

- **The packages export the input domains they enforce, so a consumer can ask instead of re-deriving.** Every `@issuegraph` package validates its own inputs, and until now almost none of that was reachable from outside — so a consumer that wanted to validate before calling in had to restate the rule, and the restatements drifted *into accepting values the library then refuses*: silent, not loud. Building `@issuegraph/cli` ([#26](https://github.com/autnmy/issuegraph/pull/26)) took six review rounds and eleven findings, four of them this. **Closes [#31](https://github.com/autnmy/issuegraph/issues/31).** The reference predicates were already exported by [#25](https://github.com/autnmy/issuegraph/pull/25), which covered three of the four domains #31 named; this closes the remaining two.
  - **`@issuegraph/reader` exports `parseRef`.** It was the single most-restated rule in the format, and the only ways to ask it were to re-implement §4.2's grammar or to feed a synthetic frontmatter block to `parseFrontmatter` and read the answer back out. The CLI did the second, and its own doc comment said why: *"does not export the function that reads them"*. A test pins the two entry points to the same verdict across every accepted and refused shape, so the export cannot drift from the parser it stands in for.
  - **It takes `unknown` and tests the type first, which is a behaviour change at the boundary and the reason the export is safe.** While the function was private every caller was internal and passed a string; exporting it makes that unenforceable, and a `string` annotation is a promise to TypeScript callers and nothing at all to JavaScript ones — the same reasoning #25 recorded for `isRefId`. Measured before the guard: `parseRef(undefined)` and `parseRef(123)` **threw a `TypeError`** rather than refusing, which would have shipped a validator that cannot be called defensively, in a package whose stated discipline is that parsing untrusted input never throws. For every string input the answers are byte-identical to before.
  - **`@issuegraph/writer` exports its splice ownership domain** — `SPLICE_OWNED_FIELDS`, `SPLICE_FIELD_OWNERSHIP`, `isSpliceOwnedField`. Which fields `spliceGeneratedEdges` owns, and which of those an explicit empty value **clears**, were previously spread across an interface, a private `switch` and a doc comment, and a consumer learned the difference by reading prose. `together-with` is absent from the domain rather than present-and-false, because the splice cannot write it at all.
  - **The private `owns()` now DERIVES from that table rather than restating it beside it.** This is the part that makes publishing it safe: the table is not a description of the behaviour, it *is* the behaviour, so the splice suite that covers clearing and preservation covers the table too. A table written alongside a hand-maintained predicate would have been one more copy of a rule this package already had three of. `clearable` carries both facts — a clearable field is owned when its property is present, a non-clearable one only when that property is non-null, because for the latter `null` is already spoken for as *leave untouched*.
  - **Totality is compile-enforced in both directions**, and the assertion's POSITION is what makes the second one work: `satisfies` sits **inside** `Object.freeze`, not after it. Excess-property checking applies only to a fresh object literal, so `Object.freeze({…}) satisfies …` checks the freeze's return value — by then the literal is spent and an extra key rides through silently. Measured: with the assertion outside, a bogus `together-with` row compiled clean while the missing-row direction failed correctly. A one-directional guard documented as two-directional is worse than none.
  - **`@issuegraph/cli` asks instead of restating, which is the proof rather than a tidy-up.** `resolveRef` calls `parseRef`; the synthetic-block probe and the `REF_CHARSET` allowlist that guarded its YAML interpolation are both **deleted**, the allowlist because there is no interpolation left to guard. `fields.ts`'s `SPLICE_WRITABLE`, `SPLICE_CLEARABLE` and `unperformableClear` derive from the writer's table. The hard-coded `unclearable` array in `verbs/write.ts` is gone.
  - **`RENDER_ONLY` stays an explicit list, and is checked for totality rather than derived as a complement.** A bare complement of `FIELDS` was tried and is wrong: `argv.ts` generates `set`'s option surface from `[...SPLICE_WRITABLE, ...RENDER_ONLY]` while `collectSetFields` handles the names it names, so a complement grows the OPTION surface the moment the specification gains a field and leaves the HANDLER behind — the new `--<field>` is parsed, accepted and silently ignored, and the command exits 0 having not done what it was asked. That is this file's own stated defect rebuilt one layer up, and strictly worse than the field being unsupported. A totality proof — this file's own `AssertTrue`/`SameKeys` idiom — makes it a BUILD ERROR instead: adding a field to the specification stops the CLI compiling until somebody classifies it, which is the moment to teach `collectSetFields` about it too. The last hand-written copy of that list, in `verbs/write.ts`, is gone with it.
  - **`CLEARABLE_JSON_KEYS` asks the CARDINALITY too, because null-clearable is narrower than clearable.** `clearable` says a field's own empty value removes it, and for a list-valued field that value is `[]`, not `null` — so a derivation filtering on `clearable` alone puts `blockedBy` in a set documented as "the keys for which an explicit `null` means REMOVE", which is false. It is asked from `@issuegraph/core`'s `EDGE_CARDINALITY`, which already owns the question. Worth recording because the wrong version was **silent**: `spliceEdges` only tests that set against the single-valued keys, and the test that would have caught it already skipped `blockedBy` by name, so nothing went red. A pin now asserts the set is exactly `serializeWith` while `blocked-by` remains clearable. The hard-coded `unclearable` array in `verbs/write.ts` is gone. #31's acceptance test was that a consumer can validate a write request *without writing a single regular expression or numeric bound of its own*; the CLI now does.
  - **No behaviour changed and no existing test was edited**, which for a published-surface change is the load-bearing claim: all 719 pre-existing assertions pass untouched. Two test labels in `refs.test.ts` were renamed because they named a probe that no longer exists — the assertions are unchanged and now prove the reader's grammar refuses an injecting token rather than proving a regex did. Giving `spliceGeneratedEdges` a distinguished result to branch on remains [#27](https://github.com/autnmy/issuegraph/issues/27), deliberately out of scope here: it overturns a pinned contract and deserves its own review.

- **SPEC 0.3.0 — a reference is an OPAQUE TRACKER-SCOPED IDENTIFIER (§4.2).** §4.2 previously defined a reference as an integer and said, in as many words, that *"no other identifier type exists in the format"*. That excluded Jira's `ABC-123` and Linear's `ENG-456` by construction, so a specification for machine-readable work relationships could not describe two of the three trackers most likely to use it. A reference is now any tracker identifier, with an optional `#` sigil and an optional `owner/repo` qualifier; `123` and `#123` denote the same issue and parse identically. The numeric shape keeps one bound — a positive, canonically-spelled, exactly-representable integer — not as arithmetic but because a value outside it comes back from a re-render spelled `1e+21`, which no reader accepts. `priority` is untouched and remains an integer 0–3.
  - **Breaking for consumers:** `IssueRef.number: number` is now `IssueRef.id: string`, and `NodeInput.number: number` is now `NodeInput.id: string`. The field is RENAMED rather than widened so every consumer breaks at compile time — a widened `number | string` leaves arithmetic on it compiling, and the order comparator subtracts two of them, which would silently yield `NaN` and an unspecified order for a non-numeric identifier.
  - **§4.2 now records that `#`-sigil references MUST be quoted**, with the failure that makes it normative rather than advice: unquoted in a flow sequence is a parse error, but unquoted in a BLOCK sequence parses successfully to `[null, null]`, with no error and no warning. An issue whose blockers silently vanished reads exactly like an issue with no blockers.
- **The reader delegates tokenizing to a maintained YAML parser.** `@issuegraph/reader` now parses with `yaml` (its first runtime dependency — zero transitive dependencies, `node >= 14.6`, comfortably under the `>=18` floor this package publishes) instead of a hand-rolled restricted-subset reader. §4.1 always required *"a plain YAML data parser"*; this makes the implementation match the rule. **Closes [#6](https://github.com/autnmy/issuegraph/issues/6)** by removing its premise rather than adjudicating it — a hand-rolled grammar for an open format yields one finding per review round indefinitely, and #6 and #10 were two instances of that one class.
  - **Safety is `parseDocument` plus a refusal on warnings, not `parse`.** With `customTags: []` an anchor raises, but an unresolved custom tag does NOT — `!!python/object 1` comes back as the string `"1"` with only a warning, so `parse` alone satisfies §4.1's anchor clause and silently fails its tag clause. Anchors are refused structurally, because `maxAliasCount` is a materializing option and cannot express the rule at parse time.
  - **Diagnostics improved rather than regressed.** A structural refusal now carries the parser's own message, which names the line, the column and the rule.
  - **The hand-rolled line grammar is gone.** `readMappingEntry`, `topLevelKeyScalar` and `stripComment` are removed from the public surface; `locateSection` replaces them, computing each entry's line span from the same document the parse reads, so an editor and a parser can no longer disagree about what an entry is. `isSectionHeader` replaces the strict header predicate. `locateBlock` and the fence patterns STAY — §4.1's canonical-block rule (first `---` block carrying the key, seen through a fence and a banner) is this specification's, not YAML's, and no frontmatter library implements it.
  - **A quoted reference is taken as written.** YAML already strips surrounding whitespace from a plain scalar, so a trim in the reference parser could only ever act on a QUOTED one — where the author explicitly asked for those bytes. `" #123 "` is refused rather than read as `123` and re-rendered as `"#123"`, which would silently change what the author wrote.
  - **`issuegraph: null` reads as an empty declaration, exactly as a bare `issuegraph:` does.** They are the same YAML value — both materialize to `{issuegraph: null}` — so the parser treats them identically rather than distinguishing two spellings of one value by reaching into the syntax tree. `locateSection` still refuses the written form, because inserting a child under a scalar value is invalid YAML: that is a fact about line-based EDITING, not about meaning, and a writer must prepend instead.
  - **`@issuegraph/derive`: the selection order is TOTAL over opaque ids.** Widening references broke transitivity in the one comparator whose whole purpose is that two clients holding the same graph derive the same order. Comparing numerically when *both* ids are numeric and falling through to a codepoint tiebreak otherwise produces a cycle as soon as one opaque id sits between two numerics the other way round — measured on `2`, `10`, `15A`: `2 < 10` numerically, `10 < 15A` and `15A < 2` by codepoint. `Array.prototype.sort` on a non-transitive comparator is input-order dependent, so that set sorted to **three different orders** depending on the order it arrived in. Each id's category is now decided from that id alone (numeric by value, then opaque by codepoint, then ids the node set does not carry), which makes the comparison lexicographic on `(category, value)` and therefore a total order. Pinned by a property test over every permutation of a mixed set, not by a pairwise assertion.
  - **`@issuegraph/core`: the reference predicates test the TYPE before the pattern.** `RegExp.test` coerces, so `isRefId(undefined)` tested the string `"undefined"` — a perfectly good opaque identifier — and returned true. A type annotation is a promise to TypeScript callers and nothing at all to the JavaScript ones a published package has, and the measured cost was a silent one: `renderRef({ repo: null, id: undefined })` emitted `"#undefined"`, which parses back as a valid reference with **zero diagnostics**. An unresolvable blocker still blocks, so the issue was left permanently unready with nothing reporting why — a writer filing a graph that lies, which is the one outcome the writer's fail-loud contract exists to make impossible. `isRefId` and `isRepoQualifier` now take `unknown` and narrow, matching `isPriority`. The Set-backed predicates never had the problem (`Set.has` does not coerce), which bounded the class to those two.
  - **SPEC §4.2 states the identifier grammar, and a test pins it to the code.** The first draft of §4.2 said an identifier was "whatever string the host tracker uses to name an issue" while the implementation admitted a bounded class — a contradiction inside this change, and one a specification cannot ship: two conforming readers would disagree about `" a b "`, and a conforming writer could emit a block its own reader cannot parse. The class is now normative (`A-Z a-z 0-9 . _ -`, opening on a letter or digit), with the three mechanisms that bound it — the writer's quoted rendering, the `#` and `/` separators, and whitespace — stated as the reasons. §4.2 also carries an accept/reject conformance table that `@issuegraph/core`'s suite reads and asserts `isRefId` against, so the prose and the predicate cannot drift; widening the class is now explicitly a spec revision rather than an implementation choice, and an unmodelled identifier fails LOUDLY on both sides (a reader diagnostic, a writer throw) rather than filing a graph that lies.
  - **A reference is read LEXICALLY, so YAML cannot retype it.** The reader took a reference from the *materialized* scalar, and YAML implicitly types a plain one — so `1e5`, `0x1F` and `007` arrived as `100000`, `31` and `7`. The first two are valid identifiers under §4.2, so an author on such a tracker had the edge silently pointed at a **different issue**; and if that substituted target happened to be closed, the issue read READY while its real blocker was open — shipping work in the wrong order, which is the one outcome this format exists to prevent. `007` additionally bypassed the canonical-number rejection §4.2's own conformance table requires. A plain scalar's identifier is now its **source text** and a quoted one's its unescaped value; `priority` and `evidence` keep the materialized value, because those genuinely *are* typed. This also removes an asymmetry previously documented as acceptable — quoted `"007"` was refused while plain `007` silently became `7`; both are refused now.
  - **Block discovery asks the parser which key a block carries, instead of matching one spelling of it.** The line prefilter cannot see a flow-root mapping — `{ issuegraph: { blocked-by: [ "#1" ] } }`, which is simply what a YAML serializer emits in flow style — so a conforming third-party writer's block was reported as **no block at all**, `data: null` with zero diagnostics and every edge silently gone. The escape-encoded and explicit-key spellings failed identically. Widening the *pattern* would have been a denylist of spellings that grows a row per review round, with every missing row another silent loss; asking the parser is total by construction. The prefilter is still OR-ed in rather than replaced, because a block that carries the key but does **not** parse must still be selected so the reader can report why — judged by the parse alone it would become invisible. Both halves are neuter-verified as load-bearing. SPEC §4.1 now states the asymmetry: readers take the key their parser reports, writers must write it literally so a tracker mirror can prefilter candidate bodies at all.
  - **`spliceGeneratedEdges` throws rather than silently losing fields it cannot edit.** Now that a flow-root block *reads*, a section that reads fine but cannot be edited line-by-line reached the same `null` return as "there is no block" — and `null` is the caller's signal to prepend, which under §4.1's first-block rule demotes the original block and drops every field the call did not own. Measured on `{issuegraph: {blocked-by: ["#1"], priority: 1, together-with: "#5"}}`: `priority` and `together-with` gone, zero diagnostics on either side. It now fails loudly, which is this package's own stated writer discipline. The throw fires **only when something would actually be lost** — an empty section, an unparseable block, and a body with no block all still return `null`. Giving callers a value to branch on instead of an exception is [#27](https://github.com/autnmy/issuegraph/issues/27).
  - **A projection never testifies that content is absent.** One class, found at two sites in the same review round, and removed rather than patched twice. (a) `blockCarriesKey` read a FAILED parse as "this block has no key", so a malformed flow-root block came back as **no block at all** — `data: null`, zero diagnostics, `isUnreadDeclaration` false — while the block-style spelling of the identical fault reported itself correctly. A failed parse cannot testify to absence; it now falls back to an unanchored key mention, which decides only whether to SELECT the block so the reader can say *why* it is unreadable. (b) `locateSection` returned `null` both for "no readable section" and for "a section I cannot edit line by line", and a caller's response to the first — prepend a fresh block — silently demotes the second under §4.1's first-block rule. It now reports `lineEditable` separately and lists the section's entries **recognised or not**, so the writer counts an author's extension field instead of the recognised-`Frontmatter` projection that omits it by design.
  - **The splice's positive control is comparative rather than a shape test.** It asked only about the RESULT — `data === null` **with** a diagnostic — so a splice that wrecked a block badly enough to make it undiscoverable produced `data: null` with **no** diagnostic (absence is silent by design) and slipped straight through: the caller was handed a non-null body and told it had succeeded, while the requested edge was unwritten and the existing fields were gone. It now compares against the body it started from — a readable declaration that stops being readable is a failed write, whatever the wreckage looks like. Intent is threaded rather than inferred, so the legitimate whole-block removal still succeeds.
  - **An empty section takes its child indent from the header.** The fallback assumed column 2, which is the header's OWN column when the block itself is indented — so a writer's first insert landed as a **sibling** of `issuegraph:` rather than a child. The body still parsed, so the post-edit readability check passed and the caller was told the write succeeded while the blocker it asked for was never readable. Silent under-blocking: the issue reads unblocked when the writer meant to block it.
  - **Behaviour deltas, all in the refusing direction.** A duplicate key — the `issuegraph` key itself, a recognised field, or an unrecognised one — now refuses the block instead of letting the first or last win silently. An empty flow-list entry (`[,]`, `[1,,2]`) refuses the block instead of yielding a partial list. A structurally invalid section refuses rather than dropping one field. One delta goes the other way: an inline flow mapping on the key (`issuegraph: {priority: 1}`) is ordinary YAML and now READS, where the hand-rolled subset refused it.
- **`@issuegraph/cli`: two inputs the libraries cannot use are refused instead of accepted.** Both were deferred from the review of [#26](https://github.com/autnmy/issuegraph/pull/26) with their consequence measured, and both are the same predicate — *a request carries a value the libraries cannot act on, and the CLI takes it anyway*. **Closes [#30](https://github.com/autnmy/issuegraph/issues/30).**
  - **A repository qualifier is asked of `@issuegraph/core`, not accepted as any string.** `asIssue` took any non-null `repo`, so `nodeKey` built a key such as `project#7` that no issue body can reference. Measured: a dependent declaring `blocked-by: project#7` came back HELD, reported as `own issuegraph declaration was not fully read (fail-safe: refusing the node)` — conservative and right, but naming the wrong thing, so a caller could not see that its own input was the defect. `isRepoQualifier` is the predicate the reader's own ref parser calls, so the CLI now asks it rather than restating the grammar or round-tripping the parser. `homeRepo` is held to the same domain for the same reason: it is not a reference, so nothing it accepts can be *mis*-resolved, but it is compared against every node's repo, and an unusable value silently matches nothing and leaves qualified keys where the caller expected bare ones.
  - **Both bounds are enforced at the boundary the two entry points SHARE, not in the JSON validator.** They first landed in `asOrderInput`, which meant `orderFromJson` had them and the exported `deriveOrder` — the same operation, reached directly — did not; a caller holding an `OrderInputDocument` can write `repo: "project"` and `number: 0` and have both type-check, so `nodeKey` rebuilt the unreferenceable `project#7` key anyway. This is the **second instance of the class `duplicateKeyRefusal` already names**, so the fix is the same one: a single `inputDomainRefusal` at `deriveOrder`, covering `repo`, `homeRepo`, `number` and `assigneeCount` together rather than the one field that was reported. Type-checking a field is not checking its domain. The parse-time readers stay — they narrow `unknown` and name the offending path for a JSON caller — and are not a second copy: each rule has one predicate and two callers. The test asserts over the entry-point table, so a third entry point is a row rather than a rediscovery.
  - **A write request naming a field the writer cannot act on is refused at the shared funnel.** `writeRequestRefusal` tested only that the request named *some* field, so `{ serialiseWith: ref }` — one letter off — passed, the writer ignored the property it does not know, and the wrapper returned the **unchanged body at exit 0**: a command telling its caller an edit happened when none did. The allowlist is an argument to `performWrite` rather than one shared list, because `set` owns seven fields and `splice` owns four — a union would wave `togetherWith` through to a splice that ignores it, which is the same defect one field along. Each list is proved to cover its interface **at compile time**, so a field added to `SetFields` or `GeneratedEdges` and not to the matching list fails the build rather than being silently refused or silently accepted. `nothing-requested` now judges values rather than key count, since `{ blockedBy: undefined }` named a key and asked for nothing. TypeScript already refused all of these (TS2561 on a literal, TS2559 through a variable, `exactOptionalPropertyTypes` on the undefined case), so the reachable population is plain-JavaScript callers — for whom a type annotation is a promise to somebody else.
- **`@issuegraph/writer`: the default written block is bare, blank-line-terminated, and auto-links.** `renderFrontmatter`'s `fenceWrapped` now defaults to `false`, refs render as quoted `"#123"` / `"owner/repo#123"`, and the block carries a blank line before its closing `---`. Measured against a live markdown renderer: that form renders as rule / paragraph / rule and auto-links every reference, where the previous fenced bare-integer output rendered neither. Auto-linking stamps a cross-reference on the TARGET issue, which is the only surface anywhere showing what an issue is blocking — §4.3.1 has no `blocks` field. The fenced form is still emitted on request and still parses; existing bodies are not migrated.

Reading and writing have opposite error disciplines on purpose: a parser takes untrusted issue text and never throws, a writer takes its caller's own data and throws before it can file an issue whose graph lies.

What a PRESENT `null` means is not uniform: on the scheduling edges (`blockedBy`, `serializeWith`) it removes, while on `decomposedFrom` and `duplicateOf` it also leaves the value alone, because the established caller shape there is "write it when the block lacks one, never clobber one that is already there" and such a caller passes `null` to mean exactly that. So those two cannot currently be CLEARED through a splice; the gap is stated rather than closed by overloading a value that already has a caller.

It also repairs ONE shape: a block inside a code fence the walk can establish. Reading the lead alone made a structural number depend on the base ranking, since which member leads is a ranking outcome, so two clients ranking differently reported different sizes for one graph.
- **The in-memory demo (`demo/`).** A live backlog running on a data source that holds one document in a variable — no tracker, no app installation, no auth, no backend — which is what makes BYO-DataSource a fact rather than a claim: a seam only ever driven by one real adapter is a seam by assertion. It loads the packages in the browser from the `exports` entries their manifests declare, through an import map, so there is nothing between the published package and the page. Every edge type, both hold families, all three readiness stations, all three rank-provenance forms and all five edge states are reachable without editing anything first, and that coverage claim is a test rather than a sentence, because a seed drifts. `failed` and `conflict` are induced from the page itself by arming what the tracker answers next. It is a **consumer**, not a package: `private: true`, and outside `packages/` on purpose, since that directory is what the isolation guard, the consumer smoke test and the lint config all read as "this ships".
  - **The order comes from `@issuegraph/derive`, not from the demo.** The store takes its deriver as a port with no default, so a host must supply one — and this host supplies the published derivation rather than a second reading of §6.2, §6.3 and §6.4. What is left on the demo's side is a PROJECTION: the store's document onto the derivation's node input, and the derivation's slots onto the stations the page draws. What stays host-side stays because the specification puts it there — the executor holds (§6.8: hold semantics are never encoded as format fields) and the concurrency cap (§6.5: dispatch policy is out of scope). Those are inputs to a derivation, not a derivation.
  - **Two defects the swap surfaced, both in the demo.** §6.7 names `blocked-by` and `serialize-with`; the demo had generalized it across both GROUP fields, drawing an unresolvable `together-with` as a non-blocking note while the reader refuses the declarer (§4.3.7 — a unit cannot be claimed atomically around a member it cannot identify), which rendered a held row with no reason on it. And a slot's serialize footprint includes its own members, so a together unit of two with no `serialize-with` edge reads 2 — tested against 1, that drew "serialized, group of 2" on a pair nothing serializes. Both were found by the test that pins every hold chip against `IssueOrderSlot.ready` in both directions, which is the point of keeping the chips as presentation over a verdict the package owns. A third, from the review: the relationships panel offered `delete` on every edge, including one that exists only as an optimistic overlay — and the store validates every non-create mutation against the LANDED document, so a click stacked an `invalid` state and a second `discard mine` onto a row that was already `failed`, and moved nothing. The control is now asked through the store's own `findEdge`, so the page cannot offer what the validator refuses — and not while an edit is in flight either, since a pending DELETE keeps its edge in `landed` until it settles and the landed answer is stale for that whole window. A fourth: the host reported `assigneeCount` for the exact ref an executor named, while §4.3.7 makes a together unit ONE atomic claim — so a third issue serialized against an unnamed member of a claimed unit read as ready. Active claims are now expanded across their together components before the projection, and the chips read the same expanded set the model was given. And a fifth, from the accessibility layer: each relationship row was itself the `role="button"`, which makes its descendants PRESENTATIONAL — so the row's own actions sat inside a control that flattens them, and the row had no accessible NAME. Read out of the browser's accessibility tree, every row came back as an unnamed `button` containing a `delete`. Selection is now a real `<button>` carrying the edge's identity with the actions as its siblings, which also deleted the two hand-written key listeners and the target guards the nesting had made necessary.
  - **One divergence is pinned, not patched.** The old deriver contracted a `together-with` unit to a single vertex before searching for cycles and the published one does not, so a `blocked-by` cycle running THROUGH a unit is no longer refused — and it is a real deadlock `Model.cycles` reports nowhere. Re-adding contraction would rebuild the second reading this removes and disagree with every other consumer, so the demo adopts the package's answer, a test pins the gap with a control, and the finding is filed against the package as [#43](https://github.com/autnmy/issuegraph/issues/43).
- **`@issuegraph/core`: `SYMMETRIC_EDGE_FIELDS` and `isSymmetricEdgeField`.** Which relationship kinds carry no direction (§4.3.4, §4.3.7) is format vocabulary, so it belongs with the rest of it rather than being rediscovered by each consumer that has to compare two edges.
- **`pnpm run ci` builds before it typechecks.** A package consuming another's published types cannot be typechecked until that one has emitted them, so on a fresh checkout the old order failed before it reached the build. Ordering it correctly is what makes a multi-package workspace check at all.
- **Import linting.** ESLint over `packages/` with `no-restricted-imports`, `import-x/no-absolute-path` and `import-x/no-relative-packages`. A real parser rather than a pattern, so template literals and comments are handled by construction. Each rule has a deliberate-violation test, and a control asserting the config matches the file.
- **Isolation guard.** `pnpm run check:isolation` refuses a forbidden dependency — by key, `npm:` alias target, or git URL — a relative import escaping its own package, and a consumer's brand token in any text a package ships, `package.json` metadata included. It scans by content rather than by an extension list, and does not exempt built output, because what a package can publish is an open set. Proved by tests that break each rule deliberately.
- **Version consistency.** SPEC.md §8 and the README both still said `v0.1.0` while the spec's own version header and this changelog said `0.2.0`. Corrected, and pinned by a test so the header and §8 cannot drift apart again.

## 0.2.0 — 2026-08-15

- §6.4 selection tiebreak: **newest first** is the default (was oldest first), with rationale — starvation avoidance now belongs to effective priority (an old issue that matters inherits urgency from its dependents), while recency buys premise freshness against issue-body rot. A deterministic executor-chosen tiebreak remains conformant.

## 0.1.0 — 2026-08-14

Initial draft.

- Carrier: standard YAML **frontmatter** on the issue body (`---`-delimited, top of body, never hidden), namespaced under a top-level `issuegraph` key. Nothing bespoke: the universal convention, on purpose.
- Fields: `blocked-by`, `decomposed-from`, `duplicate-of`, `serialize-with`, `together-with`, `priority`, `evidence`.
- No container issues: `decomposed-from` is provenance; tracking issues are replaced by queries; whole-feature gates are ordinary issues blocked by their siblings.
- `serialize-with` groups (connected components, width-1 semaphore, claim-time direction) and `together-with` units (group readiness over boundary-crossing edges, atomic claim, max effective priority, individual closure). The coordination vocabulary is closed at these two; preference fields are rejected.
- Scalar carrier precedence: established tracker conventions (priority labels, an evidence label pair) are canonical over the frontmatter; relationship fields are frontmatter-canonical.
- Writing rules bind every writer; the size rule; closure semantics (any closure unblocks, non-completed closure flags dependents for re-groom); the decision-issue pattern for nameable human gates; holds as executor policy composed via ready-and-eligible selection.
- Reading rules: ready set, backward-flowing effective priority, oldest-first tiebreak, detect-on-read cycles, fail-safe unresolvable references.
- Scope rule: the format describes work, never execution.
