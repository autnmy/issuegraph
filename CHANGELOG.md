# Changelog

Releases are recorded here. While the spec is a pre-1.0 draft, drafting churn lives in git history, not in version bumps — the version moves when there is a consumer-visible reason for it to move.

## Unreleased

- **`@issuegraph/store` `0.2.0`: the format's cardinality rule is a structural refusal, so a host has somewhere to enforce it.** Closes [#11](https://github.com/autnmy/issuegraph/issues/11). Every relationship field but `blocked-by` holds one reference (§4.3, `EDGE_CARDINALITY`), and the store enforced none of it — so the demo bolted the rule onto its adapter, the one place every write passed through, where a second `decomposed-from` came back `failed`, "refused upstream", on a write that never left the client. `structuralRefusal` now refuses it with the new code **`cardinality`**, on the same test that puts `duplicate-edge` there rather than in a guard: visible from the edit and the document, no graph walk.
  - **Asked of the RESULTING edge**, so a retype into an occupied field and a flip onto an occupied carrier are refused exactly like a create, and the edge either one replaces is excluded because it is on its way out. The carrier is `from` as written, for the symmetric kinds too — joining a group from a free carrier is how a writer joins one.
  - **Because it is structural it reaches every route to a write** — `propose`, `retry`, and the re-check an edit that waited in the queue gets — which is the property a call-site check could not have and the reason the rule kept migrating. Pinned by a store test that drives a second create through the settle window and through `retry` and counts zero dispatches.
  - **`INVALID_CODES` gains the member**, which is the semver-visible part. A host keying its sentences off the code has one more key; the editor renders the code and no sentence, so it needs nothing.
  - **The demo's adapter keeps one refusal, and it is a different one.** It no longer stands in for the store; what reaches it is the write the store cannot see — a bare `retry` after a conflict, when `landed` is deliberately unchanged and the source has moved (issue #12's window). There the tracker refuses, and `rejected` is the honest answer because the document really did move upstream.

- **`@issuegraph/viewer` `0.2.0` and `@issuegraph/editor` `0.2.0`: the cycle badge is the host's answer, so the workspace carries one.** Closes [#71](https://github.com/autnmy/issuegraph/issues/71). `clustersOf` walked the viewer's own `blocked-by` edges for whether a component contains a cycle, while `@issuegraph/reader`'s `Model.cycles` — SPEC §6.6's stuck groups, found over open issues with each together unit contracted to one vertex — answered the same question for the editor's audit overlay. Both were rendered on one screen, and they disagreed by construction on the shape [#46](https://github.com/autnmy/issuegraph/issues/46) had already fixed in the reader: `#1 blocked-by #2`, `#3 blocked-by #1`, `#2 together-with #3` is permanently stuck and closes no cycle over raw edges. `ViewerDocument` now takes **`cycles`**, required: a host fed by the reader passes `Model.cycles` verbatim and a hand-built document passes `[]`; `normalizeDocument` narrows each cycle to the keys it carries with a diagnostic per dropped member, and `clustersOf` marks a component `hasCycle` exactly when a supplied cycle names one of its members. The depth walk still steps over a closing edge, because that is what makes it terminate; it publishes nothing about it. The editor's ladder narrows the host's cycles to a focus the way it narrows edges, its rail narrows them to the window for the same reason (relayed whole, every scroll position past a stuck group published diagnostics about rows nobody asked to see), and the demo hands the viewer the same array it already hands the audit — pinned by a test that asserts the viewer capsule and the audit finding agree on the together-unit shape, and that a raw loop through a closed issue, which the reader does not report, draws no badge.
  - **Host-supplied rather than moved into `@issuegraph/core`, which the issue offered as the alternative.** The viewer keeps only the edges it can draw — a `together-with` the order does not group is dropped — so its edge set is a picture of the graph rather than the graph, and no walk over it can reach §6.6 whatever package the walk lives in; and `core`'s README promises it builds no graph and derives nothing. The rule the viewer already applies to the order applies to the cycle answer: everything it draws was given to it.
  - **Required, not optional, and that is a breaking change — hence `0.2.0`.** A cycle badge that is simply absent reads as "no cycle", so an answer a host forgot to pass must not render as an answer. The registry holds `viewer@0.1.2`; the `0.1.3` and `0.1.4` entries below never reached it, so the viewer's next release is `0.2.0` and carries all three. **The editor breaks with it**: every entry point it publishes — `renderWorkspace`, `scaleLadder`, `railWindow`, `inspectorView` — takes a `ViewerDocument`, so a host's document that was complete for `0.1.x` is a type error for this one and, from plain JavaScript, a `TypeError` inside `normalizeDocument`. That is a change to the editor's input contract, not a patch, whatever its own exports say; it takes `0.2.0`, and the `0.1.1` entry below folds into it.

- **`@issuegraph/viewer` `0.1.4`: a row's relationship badges are budgeted, so a dense document no longer explodes the linear and tree projections.** Closes [#87](https://github.com/autnmy/issuegraph/issues/87). Both projections badged every incident edge on every endpoint row with no bound of any kind — and `blocked-by` is a list field, so a valid document of a few hundred nodes admits tens of thousands of edges and the tree, which draws every key its own row, badged them all. `edgeBadges` now draws the first `ROW_BADGE_BUDGET` (12) per row in the format's field order — `blocked-by` first, because that is the relationship a reader asking "why is this held" is looking for — and collapses the rest into one `+N more relationships` chip with `data-omitted="N"` — the whole phrase in its visible text, because ARIA prohibits naming a generic span and an attribute name could be dropped by a reader.
  - **Per row, not per document, and that is the decision the issue asked for.** The graph refuses past a node budget because a canvas is a local instrument; the refusal's own last sentence promises that *the order list is complete at any size*, so a document-level budget on these projections would break the promise the refusal routes a reader to. What grows without bound on a dense document is the relationships per row, not the rows, and rows × a constant is proportionate to what these projections already draw. The third option — declaring dense documents out of scope — was declined because the consumer this gates ([autnmy/descant#11941](https://github.com/autnmy/descant/issues/11941)) embeds the viewer against repositories with thousands of open issues.
  - **Nothing is cut silently.** The chip names the count, the same rule the refusal applies to its omitted components. It carries **no** `data-ig-group`, because it names no single edge and must not enter the pointer set as if it did; an omitted edge stays selectable regardless, since `stillDrawn` answers from the document first for an edge id. The count is taken after the edge-identity dedupe, so a unit's second `edgesOf` entry for one edge is never counted as an omission.
  - **A row at or under the budget renders byte-identical to `0.1.3`**, pinned by a test at the boundary. `ROW_BADGE_BUDGET` is exported beside `GRAPH_NODE_BUDGET` so a host reads the constant rather than restating it.

- **`@issuegraph/reader` `0.6.0`: a hold is data, not only a sentence.** Closes [autnmy/descant#11277](https://github.com/autnmy/descant/issues/11277), the second residual decided in [autnmy/descant#10492](https://github.com/autnmy/descant/issues/10492). `ReadinessResult.holds` carries each failed §6.2 condition as `{ code, subject?, text }`: `code` from the closed `READINESS_HOLD_CODES` vocabulary (thirteen causes, read off the reader's own refusal sites rather than invented — `weak-source`, `under-read-self`, `closed`, `duplicate`, `blocked-by-open`, `blocked-by-under-read`, `blocked-by-unresolvable`, `relation-unresolvable`, `together-under-read`, `together-member-unready`, `serialize-under-read`, `serialize-claimed`, `unknown-node`), `subject` the issue the cause names when it names one — the open blocker, the claimed serialize peer, the unready unit member, or an unresolvable reference, always as the model's key (an unresolvable ref is normalized to the key it would have had, never left as the declaration's raw text) — and `text` the sentence `reasons` has always carried, byte for byte.
  - **`reasons` stays, as a projection.** `reasons` is `holds.map((h) => h.text)` in the same order, derived in one place — the source-and-projection rule `ParseResult.findings` and `diagnostics` set in `0.3.0`, for the same reason: two hand-maintained lists drift. Every consumer that reads prose reads exactly what it read before; the surface is a superset. A test pins the projection over every key of the vocabulary corpus, and a per-code table pins each sentence beside its code so a reworded hold fails a test rather than shipping as prose only. The unknown-key refusal is one shared value, so `readiness` and `buildModel`'s fallback cannot spell it differently.
  - **Why the reader and not the viewer.** The loss was measured at `baseReasons`, which knew the discriminated cause and flattened it to a sentence on the spot; a `code` added only to `ViewerHold` would have had the host recover it by parsing the prose it had just been handed — the exact matching this exists to end, moved one layer down. The subject is the half that matters: every held unit whose holder is not among its drawn members named that holder only in prose.
  - **`@issuegraph/derive` `0.1.6`** — `IssueOrderSlot.holds`, the union over a unit's members deduplicated by sentence exactly as `holdReasons` is, and `holdReasons` is now derived from it in the same pass. **`@issuegraph/cli` `0.3.3`** — `order` and `ready` slots carry `holds` beside `holdReasons`; nothing in the verb changed. **`@issuegraph/writer` `0.3.3`** goes with them for the reason it always does: published against `@issuegraph/reader@^0.5.0`, which `0.6.0` does not admit, so `check:publishable` would report a stranding.
  - **`@issuegraph/viewer` `0.1.3`** — `ViewerHold.code?` and `.subject?`, host-authored like `reason` and typed as strings because the vocabulary is the reader's and this layer restates nothing; `holdLine` publishes them as `data-code` and `data-subject` beside `data-family`, omitted rather than emptied when absent. **`@issuegraph/editor` `0.1.1`** — the inspector's hold rows carry the same two attributes, and a `subject` is rendered as a `select-issue` control naming it, so the holder becomes a deep link into the one selection every zone shares through the reducer that already answers the relationship rows.
  - **Out of scope, deliberately.** The demo's own `Hold` vocabulary (its derivation is separate, and [#94](https://github.com/autnmy/issuegraph/issues/94) restructures the demo), and a per-cause filter facet in the editor: the data now carries `code`, and a facet is a rail control with a design of its own.

- **`@issuegraph/editor` `0.1.1`: a dead-duplicate finding names the closed canonical it is about.** Closes [autnmy/descant#10401](https://github.com/autnmy/descant/issues/10401), deferred from [#69](https://github.com/autnmy/issuegraph/pull/69)'s review. A `dead-duplicate-ref` finding's `members` named the edge's two ends and nothing else, on the reasoning that those are what an owner edits — so when the document carried the target under its bare ref while the edge named it qualified (`a duplicate-of acme/app#2`, carried as `2`, both spellings legal under SPEC §4.2), the host translated correctly and the finding fired, but `acme/app#2` is not a ref the overlay carries, it was dropped, and the closed target the finding is centrally about carried no bar and failed the audit filter. The members now name the declarer, the immediate target, and the canonical the chain resolves to; a set collapses the ordinary same-spelling case back to two, and in a resolved chain (`a → b → c`) `a`'s finding now says on `c` what its `detail` already said. The detector cannot tell a spelling from a hop and does not need to — one rule covers both.
  - **`stale-blocker` deliberately does NOT follow.** Its members stay the two ends: the remedy sits on the declarer's edge, so a `misleading` bar on the closed canonical would mark a row with nothing to do there, and the spelling shape cannot reach it anyway — a target the document does not carry is never resolved on the target side, so that finding is withheld as unknown rather than mis-membered. Pinned by a test and recorded at the call site, as the fifth decided asymmetry between the two edge classes.

- **`@issuegraph/reader` `0.5.0`: `Model` carries the two accessors a host had to derive beside it, and `decomposed-from` provenance is diagnosed.** Closes [#95](https://github.com/autnmy/issuegraph/issues/95). `autnmy/descant` adopted `buildModel` and kept a local derivation of two things its scheduler reads — a second reader of the edge loop's own rule, kept only because the package did not carry them. It carries them now, additively:
  - **`Model.priorityInheritors(key)`** — the OPEN nodes that inherit `key`'s priority under §6.3, as sorted canonical keys, excluding the key itself. It is the transitive closure over the SAME relation the effective-priority fold relaxes (open `blocked-by` targets and the other members of the together unit), and that relation is now defined once inside `buildModel` and consumed by both walks, so they cannot disagree. Declarer-only nodes are traversed through but never returned (`keys`' contract); duplicates are never returned (`readiness`' own test — a `duplicate-of` cycle or set-exit has no canonical to offer, and emitting the still-duplicate key reads as work that exists). Empty for an unknown key and for a closed one. A closure rather than a one-hop neighbourhood on purpose: two prose derivations of this set were each short in a different place (autnmy/descant#11568).
  - **`Model.serializeHorizonTruncated(key)`** — whether any member of `key`'s serialize component declared a `serialize-with` the node set could not resolve, so the component's true extent is unknown. NOT folded into `readiness` — §6.7 says an unresolvable `serialize-with` contributes no linkage — and recorded in its own set rather than read back off the diagnostic text, so a reworded message cannot fail it open. Exposed so a host that knows its own traversal depth can compose the refusal (autnmy/descant#9206).
  - **A provenance diagnostic for an unresolvable `decomposed-from`** — `<key>: decomposed-from <ref> is unresolvable in this node set; provenance only, so no readiness effect`. A diagnostic and nothing else: the field feeds no edge map and enters no refusal ledger, so no readiness answer changes (autnmy/descant#7177). It is how a neighbourhood seeder learns the set it assembled is missing the issue a split came from.
  - **`@issuegraph/cli`, `@issuegraph/derive` and `@issuegraph/writer` go with it, for a reason that is not their own code.** All three are published against `@issuegraph/reader@^0.4.0`, which `0.5.0` does not admit, so a release publishing only the reader would leave them resolving the old one; `check:publishable` reports that as a stranding. Nothing in any of the three changed.

- **`@issuegraph/writer` `0.3.2` and `@issuegraph/reader` `0.5.0`: a comment inside an owned entry survives the splice.** Closes [#93](https://github.com/autnmy/issuegraph/issues/93). The reader reports `blocked-by:` as one span from the key line to its last item, so a comment an author wrote between them — an owner ruling recorded beside the gate it explains — sat inside the removed range without being part of the edge, and `0.3.0` deleted it. The writer owns the edges, not the commentary: a comment-only line inside an owned span is now kept, which is the rule the private writer this package replaced already had — after a refresh it sits directly behind the rendered entry; after a clear it sits where the entry was, re-indented to the indent of the context it now lives in — the section's child indent, or the block's top level when the bare `issuegraph:` header goes with the entry — so it cannot be read as the continuation of a neighbour's block scalar (raised in review twice: kept at the item indent behind `notes: |` inside the section, and at the child indent behind a top-level `notes: |` once the header was dropped, it became one more line of `notes` each time, a field the post-condition does not compare). A blank line inside a span still goes, and so does a comment when the edit leaves the block with nothing else in it — the whole-block removal is the one edit that removes a comment, and the README says so. A kept comment is not counted as section content, so an emptied section is still detected as empty. The versions are the ones the entry above published, not the `0.3.1` / `0.4.0` this entry first named: that release was cut from [#97](https://github.com/autnmy/issuegraph/pull/97) minutes before [#96](https://github.com/autnmy/issuegraph/pull/96) merged, so `writer@0.3.1` and `reader@0.4.0` on the registry do NOT carry this change — `check:publishable` read both as STALE until [#99](https://github.com/autnmy/issuegraph/pull/99) moved them. A consumer wanting the fix pins `writer@0.3.2` / `reader@0.5.0` or later.
  - **Which lines are comments is the reader's answer, not the writer's guess.** `@issuegraph/reader`'s `SectionField` gains `commentLines`: the interior line indices inside each span that are nothing but a comment, read off the `yaml` concrete syntax tree from the same tokenizer `parseDocument` runs. Raised in review: `#123` under `duplicate-of: |-` is a block scalar's content and a ref the reader accepts, and a shape test on the line kept it as a comment, leaving the old value as debris beneath the rendered entry. Same seam, same rule as the spans themselves — one opinion about the bytes. A trailing comment on a content line is not listed, because that line is content. Additive: a consumer reading `SectionField` sees one more field.

- **`@issuegraph/reader` `0.4.0` and `@issuegraph/writer` `0.3.1`: a comment-only entry no longer swallows the sibling under it.** Closes [#92](https://github.com/autnmy/issuegraph/issues/92). A `blocked-by` list whose items are all the unquoted-sigil shape a hand author writes — `- #9094`, which YAML reads as an empty item carrying a comment — gave `locateSection` a span one line too long, so `spliceGeneratedEdges` removed the recognised field directly beneath it (`evidence: verified`, or a `serialize-with`) along with the owned entry. The result read perfectly and the owned field was exactly what was asked for, so the call reported success. Measured on descant's corpus, whose reader-side round-trip probe had been refusing every such block as unread to avoid exactly this loss.
  - **The cause is the parser's node end, and it is wider than lists.** For a node that is empty with a comment, the `yaml` range end sits on the FIRST CONTENT BYTE OF THE NEXT LINE, not after the newline — so `range[2] - 1` is the sibling's indentation, and the step-back that crossed blank *lines* had nothing blank to cross. A comment-only scalar (`serialize-with: #7`) and a mixed list (`- 1` then `- #9094`) mis-spanned the same way. One rule replaces the two shapes: an entry ends on the line holding the last non-whitespace BYTE its node put in the text, which stops on a value or on the node's own trailing comment and never on a sibling. The blank-line case is subsumed rather than kept beside it.
  - **The writer now verifies the third question.** [#55](https://github.com/autnmy/issuegraph/pull/55)'s post-condition compared owned fields only, which [#58](https://github.com/autnmy/issuegraph/issues/58) recorded as a latent gap; this is the gap, hit. `settle` now also compares every recognised field the call did NOT own — `priority`, `evidence`, `together-with`, and any owned field the call omitted — between the before and after parses, and answers `not-written` naming the field on a difference. The comparison is `unownedFieldMismatch`, exported and tested directly, because with the reader fixed nothing in this repository can reach the arm through the public API — and a guard whose failing case no test can build is one nobody can check. Where it still fires is the version-skew case these `0.x` packages allow: a consumer pairing this writer with a reader that mis-spans gets a refusal where it used to get silent loss. #58's other half — the line-level "every un-removed line appears verbatim" assertion — is untouched and stays open there.
  - **What the span still includes is unchanged, deliberately.** A comment line inside an owned entry's own item list is still part of that entry's span; whether it should be is [#93](https://github.com/autnmy/issuegraph/issues/93)'s question, not this one's.
- **`@issuegraph/reader` `0.4.0`: readiness and the two group resolutions become individually callable.** Closes [#83](https://github.com/autnmy/issuegraph/issues/83), which is [#14](https://github.com/autnmy/issuegraph/issues/14)'s last open Done-when. `deriveIssueOrder` and `wouldCycleOnBlockedBy` were already individually callable; **readiness**, **serialize-group resolution** and **`together-with` unit resolution** were reachable only by running the whole derivation and reading its output — so a scheduler asking *"is this candidate ready?"* per candidate paid for a full model build over the corpus, once per candidate. `evaluateReadiness`, `resolveSerializeGroup` and `resolveTogetherUnit` answer one question about one issue.
  - **An EXTRACTION, not a second implementation, and that is the whole design.** The three derivations moved into `relations.ts` and `buildModel` now CALLS them — the model is a layer *on top of* that file rather than a second opinion beside it. `Model.readiness` and `evaluateReadiness` are one function reached two ways, so they cannot drift; the same rule `model.ts` already states for its relationship to `@issuegraph/derive`, applied one layer down. A test sweeps **every** key of a mixed corpus asserting all three answers match the model's, because a divergence introduced later will not be in the case whoever wrote it was thinking about.
  - **The saving is what a single question no longer builds**, measured as deterministic operation counts rather than as a duration, because a timing assertion proves nothing about *which* work was skipped and flakes under load. Against a 2,000-node set, one question falls from **2,000 priority resolutions and ~163,900 node-declaration reads to 0 and ~2,014**. What it does not remove is the edge pass over the supplied nodes, and that is inherent: a `serialize-with` edge is declared by the node that holds it, so any node may pull a peer into your component and no correct answer is available without reading every declaration. The README says so rather than implying the cost away, and says the other half too — **for many questions, build the model once**, which amortises exactly the pass these cannot avoid.
  - **The cost property is pinned by a test, using `labels` as the probe.** It is read by exactly one layer — `buildModel`'s declared-priority pass calls `priorityLabelValue(node.labels)` once per node — and by no part of readiness or component resolution. So a labels read witnesses that the priority layer ran, and its absence witnesses that a single question did not pay for one. Verified by negative control: routing `evaluateReadiness` through the full model turns the test red, naming the 50 reads it saw.
  - **The component tables materialize on first ask.** Each is a scan of every key plus a sort per component, and `resolveTogetherUnit` never needs the serialize table nor `resolveSerializeGroup` the together one. Still built at most once per call, so `buildModel` — which reads both — pays exactly what it paid before.
  - **`deriveIssueOrder` composes them, and a test says so on the reference seed.** It reaches them through `buildModel`, which reaches them through the same functions the assertions call, so today it holds by construction — which is precisely why it is worth pinning: the failure guarded against is a later change that "optimises" one of these answers inside the derivation while the standalone entry points keep saying something else, which nothing else in the suite would notice because both paths have their own passing tests. The seed carries no held slot, so a fixture with one is built beside it; its deduplicated `holdReasons` is the assertion with teeth, verified red when the derivation stops deduplicating.
  - **One thing the tests could NOT distinguish is recorded rather than papered over.** Mutating the derivation's `members.every((m) => model.readiness(m).ready)` to `members.some(...)` leaves the suite green, and correctly: `readiness` is already unit-aware — it appends a `together member ... is not ready` reason to every member — so all members of a unit share one readiness and the quantifiers cannot differ. The `every` is a restatement of a guarantee the relation layer already gives. It is left as the honest spelling of the intent, with a note so the next reader does not mistake the absence of a failing test for an untested branch.
  - **Behaviour is unchanged and the public surface is a superset.** The node types, key helpers and `ModelOptions` are re-exported from `model.ts` unchanged — `ModelOptions` is now an alias of the shared `RelationsOptions`, so a field added for one can never be missing from the other — and all 186 pre-existing tests pass untouched. `Relations` itself is deliberately **not** on the barrel: it hands out live mutable structures and its shape is an implementation detail of the split.
  - **`@issuegraph/cli` `0.3.1`, `@issuegraph/derive` `0.1.4` and `@issuegraph/writer` `0.3.1` go with it, for a reason that is not their own code.** All three are published against `@issuegraph/reader@^0.3.0`, which `0.4.0` does not admit, so a release publishing only the reader would leave them resolving the old one. `check:publishable` reports that as a stranding rather than letting the release make it — the same mechanism that took `derive` to `0.1.3` in the entry above. Nothing in any of the three changed.

- **`@issuegraph/reader` `0.3.0`: `ParseResult` says WHICH FIELD it lost, not just that it lost something.** Closes [#78](https://github.com/autnmy/issuegraph/issues/78). `diagnostics` answered the TOTAL question — was anything in this block lost? — so a consumer gating admission on `blocked-by` had to refuse a body whose `blocked-by` read perfectly and whose `priority` next door did not. Every gate was as strict as the most damaged field anywhere in the block, which is fail-closed and therefore safe, and is exactly why it went unnoticed: it makes per-field gates unbuildable, because one unrecognised extension field anywhere refuses every gate in the system. The attribution already existed INSIDE the parser — it knows which field it is dropping at the moment it drops it — and only the reporting stopped at the package boundary.
  - **`findings` is the source and `diagnostics` is now a PROJECTION of it**, one message each in the same order, rather than a second array maintained beside it. Two hand-maintained lists drift, and a drifted pair reports a loss to one reader and not the other — which is the failure the field exists to end, reintroduced one level down. The accumulator inside `parseFrontmatter` was replaced rather than supplemented, so a diagnostic site that forgot to attribute itself does not compile; `refsFrom` takes the attributing sink and names its own field, because a PARTIAL drop (`blocked-by: [123, "not a ref"]` returns a non-empty list) is invisible to anything outside it.
  - **`isUnreadDeclarationFor(parse, fields)` asks the narrowed question**, alongside `isUnreadDeclaration` and on the same argument that justified exporting the broad one: the QUESTION factors and the POLICY does not. Two properties are pinned by tests rather than asserted in prose — a `block`-scoped finding answers true to **every** query including the empty set, because a structural loss makes the block's contents unknowable and a narrowed reader must refuse where the broad one does; and asking for the full field set reproduces `isUnreadDeclaration` **exactly**, which is what stops the two predicates drifting apart when a future field forgets to attribute itself.
  - **`Finding.field` is `@issuegraph/core`'s `Field`, not a fresh string union.** The vocabulary has one home, and a second spelling of it in the reader would be free to drift from `FIELDS` the moment the spec adds a field. `singleRef` was retyped from `string` to `Field` to carry it, which the `isField` guard above the switch already guaranteed.
  - **The three routes a consumer was left with are all closed, and each one looks available until it is tried.** String-matching the message prose fails **open** under a rewording — the route consumers actually took. Comparing `locateSection().fields` against `data` catches a field dropped entirely and not a partial drop, and `SectionField` spans cannot close that: they are degenerate for a flow section by documented design, so item-level counting is unavailable exactly where it is needed. Re-parsing the block's YAML is a second opinion about what an entry is, which is the seam `locateSection` was introduced to eliminate after three defects were filed against it.
  - **Additive for every consumer**: `ParseResult` is a return type and `parseFrontmatter` is the only thing in the repository that constructs one, so the new required field breaks nothing that reads a parse. A consumer that structurally builds its own `ParseResult` literal would need the field; none exists here.
  - **`@issuegraph/derive` goes to `0.1.3` for a reason that is not its own code.** It is published at `0.1.2` and byte-identical, so the release would SKIP it — leaving the published copy pinned to `@issuegraph/reader@^0.2.1`, which `0.3.0` does not admit, and a consumer installing both would silently keep resolving the old reader. `check:publishable` reports that as a stranding rather than letting the release make it. Nothing in `derive` changed: it consumes `buildModel`, `Model`, `NodeInput` and `IssueRef`, none of which this touches.

  - **The pre-write guard builds its OWN together components, spanning closed nodes.** `Model.togetherComponent` unions only open endpoints — correctly, because "a closed member has left the unit" is true of readiness today — so a unit with a closed member is invisible to it. The guard is asked about the future: with `#1 blocked-by #2` and a **closed** `#2 together-with #3`, it admitted `#3 blocked-by #1`, and reopening `#2` then produced the permanent cycle it exists to refuse, with the edge already written. `buildTogetherComponents` walks the raw declarations, the same shape `buildBlockedByAdjacency` already uses for the other edge kind and for the same reason — divergence 1 applied to the other axis.
  - **The demo found it, and its known-gap pin is now an assertion.** [#9](https://github.com/autnmy/issuegraph/pull/9) replaced the demo's hand-rolled deriver — which *did* contract — with `@issuegraph/derive`, and rather than keep a second reading of the rules the demo pinned the difference as a failing-when-fixed test. It fired on this change, exactly as its comment said it would.

- **`@issuegraph/core` 0.1.1 — republished, because the published `0.1.0` cannot satisfy the consumers that depend on it.** `core@0.1.0` predates `isRefId` and `isRepoQualifier`, which [#25](https://github.com/autnmy/issuegraph/pull/25) added without moving the version. `pnpm publish --recursive` publishes only versions the registry does not already hold, so the next release **skipped `core` silently, at exit 0**, and published `@issuegraph/reader@0.2.0` and `@issuegraph/writer@0.1.0` — both of which import those two names, and both of which pnpm had rewritten to depend on `core@^0.1.0`, the stale tarball. Every fresh `npm install @issuegraph/cli` then threw on import: the binary exited 1 on every invocation and `import('@issuegraph/cli')` failed identically. **Closes [#36](https://github.com/autnmy/issuegraph/issues/36).** No source changed; this is a publish, not a fix.
  - **A PATCH bump, and the distinction is the whole repair rather than a style choice.** Every already-published consumer pins `core@^0.1.0`, and a caret on a `0.x` version pins the MINOR — so `^0.1.0` admits `0.1.1` and does **not** admit `0.2.0`. Publishing `0.1.1` repairs `reader@0.2.0`, `writer@0.1.0`, `derive@0.1.0` and `cli@0.1.0` **without republishing any of them**. Publishing `0.2.0` — the version "it adds exports, so it is a minor" argues for — would have left every one of them resolving the old `core` and reproduced the bug while looking like its fix. Measured end to end: the broken graph exits 1, and overlaying `core@0.1.1` alone takes `issuegraph parse` to exit 0 on a body with no block.
  - **The change is additive only.** `core` gains `SYMMETRIC_EDGE_FIELDS`, `isRefId`, `isRepoQualifier` and `isSymmetricEdgeField`; nothing was removed, renamed or revalued, so a consumer already resolving `0.1.0` cannot be broken by resolving `0.1.1` instead.

- **A guard that compares what a release would publish against what the registry already holds (`pnpm check:publishable`).** The reason #36 reached the registry unnoticed is that nothing asked this question. `ci.yml` builds and tests the workspace, where `workspace:^` always resolves to the local `core` — the one configuration that cannot fail — and `smoke-consumer.mjs` loads `dist` through that same link. Both are green in precisely the arrangement no consumer is ever in. It runs as the last gate before the irreversible step in `publish.yml` — on dry runs too, so a release can be rehearsed to find out what needs bumping. Deliberately **not** a per-PR job: this file's own release discipline says drafting churn lives in git history rather than in version bumps, so between releases a package's content is *expected* to have drifted from its published version, and a per-PR gate would red every pull request that edits package source. Its decision logic is still covered on every PR by `scripts/check-publishable.test.ts`.
  - **It asks two questions, and the second exists because the first opens a hole.** *Staleness*: did a package's authored content change while its version did not? That is #36, and a bump is the answer. Ranges the SOURCE manifest declares through the `workspace:` protocol are excluded from that comparison because pnpm derives them at pack time — bumping `core` alone rewrote the manifest of all four packages that depend on it, at nothing but `^0.1.0` → `^0.1.1`, and blocking a release on that is a false positive on a correct tree. *Resolvability* closes what the exclusion loses: a published consumer that is not being republished keeps the range it already carries, so the guard asks whether that range still admits the version this release uploads. Both are proven to fire — reverting the bump reports `core` STALE, and setting it to `0.2.0` reports all four consumers STRANDED. The blanking is narrow in both directions: it keeps the authored OPERATOR and drops only the derived version, so tightening `workspace:^` to `workspace:~` without a bump is still reported; and it keys on the DECLARATION rather than the package name, so a literal `"@issuegraph/core": "^0.1.0"` changed to `^0.2.0` without a bump is reported too. pnpm rewrites `workspace:` at pack time, so only the source manifest can say which ranges were derived.
  - **The control the issue prescribed was measured and does not work.** Packing every package, installing the tarballs into a scratch directory and importing them passes on the broken tree: the locally packed `core` satisfies the rewritten `^0.1.0`, so the stale published tarball is never fetched. A control that passes on the defect it was added for is decoration, and it is recorded here so it is not proposed again.
  - **An unreachable registry is `unknown`, never `new`.** Reading a transport failure as "not published" would wave through exactly the change the guard exists to stop, at the moment the network is the reason nobody can see the conflict. It fails closed and names the package it could not resolve. The range predicate is likewise an allowlist of two shapes — an exact version and a caret — returning `undefined` for anything else rather than guessing, because a wrong *admits* is the answer that ships the bug.

- **The packages export the input domains they enforce, so a consumer can ask instead of re-deriving.** Every `@issuegraph` package validates its own inputs, and until now almost none of that was reachable from outside — so a consumer that wanted to validate before calling in had to restate the rule, and the restatements drifted *into accepting values the library then refuses*: silent, not loud. Building `@issuegraph/cli` ([#26](https://github.com/autnmy/issuegraph/pull/26)) took six review rounds and eleven findings, four of them this. **Closes [#31](https://github.com/autnmy/issuegraph/issues/31).** The reference predicates were already exported by [#25](https://github.com/autnmy/issuegraph/pull/25), which covered three of the four domains #31 named; this closes the remaining two.
  - **`@issuegraph/reader` exports `parseRef`.** It was the single most-restated rule in the format, and the only ways to ask it were to re-implement §4.2's grammar or to feed a synthetic frontmatter block to `parseFrontmatter` and read the answer back out. The CLI did the second, and its own doc comment said why: *"does not export the function that reads them"*. A test pins the two entry points to the same verdict across every accepted and refused shape, so the export cannot drift from the parser it stands in for.
  - **It takes `unknown` and tests the type first, which is a behaviour change at the boundary and the reason the export is safe.** While the function was private every caller was internal and passed a string; exporting it makes that unenforceable, and a `string` annotation is a promise to TypeScript callers and nothing at all to JavaScript ones — the same reasoning #25 recorded for `isRefId`. Measured before the guard: `parseRef(undefined)` and `parseRef(123)` **threw a `TypeError`** rather than refusing, which would have shipped a validator that cannot be called defensively, in a package whose stated discipline is that parsing untrusted input never throws. For every string input the answers are byte-identical to before.
  - **`@issuegraph/writer` exports its splice ownership domain** — `SPLICE_OWNED_FIELDS`, `SPLICE_FIELD_OWNERSHIP`, `isSpliceOwnedField`. Which fields `spliceGeneratedEdges` owns, and which of those an explicit empty value **clears**, were previously spread across an interface, a private `switch` and a doc comment, and a consumer learned the difference by reading prose. `together-with` is absent from the domain rather than present-and-false, because the splice cannot write it at all.
  - **The private `owns()` now DERIVES from that table rather than restating it beside it.** This is the part that makes publishing it safe: the table is not a description of the behaviour, it *is* the behaviour, so the splice suite that covers clearing and preservation covers the table too. A table written alongside a hand-maintained predicate would have been one more copy of a rule this package already had three of. `clearable` carries both facts — a clearable field is owned when its property is present, a non-clearable one only when that property is non-null, because for the latter `null` is already spoken for as *leave untouched*.
  - **Totality is compile-enforced in both directions**, and the assertion's POSITION is what makes the second one work: `satisfies` sits **inside** `Object.freeze`, not after it. Excess-property checking applies only to a fresh object literal, so `Object.freeze({…}) satisfies …` checks the freeze's return value — by then the literal is spent and an extra key rides through silently. Measured: with the assertion outside, a bogus `together-with` row compiled clean while the missing-row direction failed correctly. A one-directional guard documented as two-directional is worse than none.
  - **`@issuegraph/cli` asks instead of restating, which is the proof rather than a tidy-up.** `resolveRef` calls `parseRef`; the synthetic-block probe and the `REF_CHARSET` allowlist that guarded its YAML interpolation are both **deleted**, the allowlist because there is no interpolation left to guard. `fields.ts`'s `SPLICE_WRITABLE`, `SPLICE_CLEARABLE` and `unperformableClear` derive from the writer's table. The hard-coded `unclearable` array in `verbs/write.ts` is gone.
  - **`RENDER_ONLY` stays an explicit list, and is checked for totality rather than derived as a complement.** A bare complement of `FIELDS` was tried and is wrong: `argv.ts` generates `set`'s option surface from `[...SPLICE_WRITABLE, ...RENDER_ONLY]` while `collectSetFields` handles the names it names, so a complement grows the OPTION surface the moment the specification gains a field and leaves the HANDLER behind — the new `--<field>` is parsed, accepted and silently ignored, and the command exits 0 having not done what it was asked. That is this file's own stated defect rebuilt one layer up, and strictly worse than the field being unsupported. A totality proof — this file's own `AssertTrue`/`SameKeys` idiom — makes it a BUILD ERROR instead: adding a field to the specification stops the CLI compiling until somebody classifies it, which is the moment to teach `collectSetFields` about it too. The last hand-written copy of that list, in `verbs/write.ts`, is gone with it.
  - **`CLEARABLE_JSON_KEYS` asks the CARDINALITY too, because null-clearable is narrower than clearable.** `clearable` says a field's own empty value removes it, and for a list-valued field that value is `[]`, not `null` — so a derivation filtering on `clearable` alone puts `blockedBy` in a set documented as "the keys for which an explicit `null` means REMOVE", which is false. It is asked from `@issuegraph/core`'s `EDGE_CARDINALITY`, which already owns the question. Worth recording because the wrong version was **silent**: `spliceEdges` only tests that set against the single-valued keys, and the test that would have caught it already skipped `blockedBy` by name, so nothing went red. A pin now asserts the set is exactly `serializeWith` while `blocked-by` remains clearable. The hard-coded `unclearable` array in `verbs/write.ts` is gone. #31's acceptance test was that a consumer can validate a write request *without writing a single regular expression or numeric bound of its own*; the CLI now does.
  - **No behaviour changed and no existing test was edited**, which for a published-surface change is the load-bearing claim: all 719 pre-existing assertions pass untouched. Two test labels in `refs.test.ts` were renamed because they named a probe that no longer exists — the assertions are unchanged and now prove the reader's grammar refuses an injecting token rather than proving a regex did. Giving `spliceGeneratedEdges` a distinguished result to branch on remains [#27](https://github.com/autnmy/issuegraph/issues/27), deliberately out of scope here: it overturns a pinned contract and deserves its own review.

- **SPEC 0.3.0 — a reference is an OPAQUE TRACKER-SCOPED IDENTIFIER (§4.2).** §4.2 previously defined a reference as an integer and said, in as many words, that *"no other identifier type exists in the format"*. That excluded Jira's `ABC-123` and Linear's `ENG-456` by construction, so a specification for machine-readable work relationships could not describe two of the three trackers most likely to use it. A reference is now any tracker identifier, with an optional `#` sigil and an optional `owner/repo` qualifier; `123` and `#123` denote the same issue and parse identically. The numeric shape keeps one bound — a positive, canonically-spelled, exactly-representable integer — not as arithmetic but because a value outside it comes back from a re-render spelled `1e+21`, which no reader accepts. `priority` is untouched and remains an integer 0–3.
  - **Breaking for consumers:** `IssueRef.number: number` is now `IssueRef.id: string`, and `NodeInput.number: number` is now `NodeInput.id: string`. The field is RENAMED rather than widened so every consumer breaks at compile time — a widened `number | string` leaves arithmetic on it compiling, and the order comparator subtracts two of them, which would silently yield `NaN` and an unspecified order for a non-numeric identifier.
  - **§4.2 now records that `#`-sigil references MUST be quoted**, with the failure that makes it normative rather than advice: unquoted in a flow sequence is a parse error, but unquoted in a BLOCK sequence parses successfully to `[null, null]`, with no error and no warning. An issue whose blockers silently vanished reads exactly like an issue with no blockers.
- **The reader delegates tokenizing to a maintained YAML parser.** `@issuegraph/reader` now parses with `yaml` (its first runtime dependency — zero transitive dependencies, `node >= 14.6`, comfortably under the `>=18` floor this package publishes) instead of a hand-rolled restricted-subset reader. §4.1 always required *"a plain YAML data parser"*; this makes the implementation match the rule. **Closes [#6](https://github.com/autnmy/issuegraph/issues/6)** by removing its premise rather than adjudicating it — a hand-rolled grammar for an open format yields one finding per review round indefinitely, and #6 and #10 were two instances of that one class.
  - **Safety is `parseDocument` plus a refusal on warnings, not `parse`.** With `customTags: []` an anchor raises, but an unresolved custom tag does NOT — `!!python/object 1` comes back as the string `"1"` with only a warning, so `parse` alone satisfies §4.1's anchor clause and silently fails its tag clause. Anchors are refused structurally, because `maxAliasCount` is a materializing option and cannot express the rule at parse time.
  - **Diagnostics improved rather than regressed.** A structural refusal now carries the parser's own message, which names the line, the column and the rule.
  - **The hand-rolled line grammar is gone.** `readMappingEntry`, `topLevelKeyScalar` and `stripComment` are removed from the public surface; `locateSection` replaces them, computing each entry's line span from the same document the parse reads, so an editor and a parser can no longer disagree about what an entry is. `isSectionHeader` replaces the strict header predicate. `locateBlock` and the fence patterns STAY — §4.1's canonical-block rule (first `---` block carrying the key, seen through a fence and a banner) is this specification's, not YAML's, and no frontmatter library implements it.
  - **A quoted reference is taken as written.** YAML already strips surrounding whitespace from a plain scalar, so a trim in the reference parser could only ever act on a QUOTED one — where the author explicitly asked for those bytes. `" #123 "` is refused rather than read as `123` and re-rendered as `"#123"`, which would silently change what the author wrote.
  - **`issuegraph: null` reads as an empty declaration, exactly as a bare `issuegraph:` does.** They are the same YAML value — both materialize to `{issuegraph: null}` — so the parser treats them identically rather than distinguishing two spellings of one value by reaching into the syntax tree. `locateSection` still refuses the written form, because inserting a child under a scalar value is invalid YAML: that is a fact about line-based EDITING, not about meaning, and a writer must prepend instead.
  - **`@issuegraph/derive`: the selection order is TOTAL over opaque ids.** Widening references broke transitivity in the one comparator whose whole purpose is that two clients holding the same graph derive the same order. Comparing numerically when *both* ids are numeric and falling through to a codepoint tiebreak otherwise produces a cycle as soon as one opaque id sits between two numerics the other way round — measured on `2`, `10`, `15A`: `2 < 10` numerically, `10 < 15A` and `15A < 2` by codepoint. `Array.prototype.sort` on a non-transitive comparator is input-order dependent, so that set sorted to **three different orders** depending on the order it arrived in. Each id's category is now decided from that id alone (numeric by value, then opaque by codepoint, then ids the node set does not carry), which makes the comparison lexicographic on `(category, value)` and therefore a total order. Pinned by a property test over every permutation of a mixed set, not by a pairwise assertion.
  - **`@issuegraph/core`: the reference predicates test the TYPE before the pattern.** `RegExp.test` coerces, so `isRefId(undefined)` tested the string `"undefined"` — a perfectly good opaque identifier — and returned true. A type annotation is a promise to TypeScript callers and nothing at all to the JavaScript ones a published package has, and the measured cost was a silent one: `renderRef({ repo: null, id: undefined })` emitted `"#undefined"`, which parses back as a valid reference with **zero diagnostics**. An unresolvable blocker still blocks, so the issue was left permanently unready with nothing reporting why — a writer filing a graph that lies, which is the one outcome the writer's fail-loud contract exists to make impossible. `isRefId` and `isRepoQualifier` now take `unknown` and narrow, matching `isPriority`. The Set-backed predicates never had the problem (`Set.has` does not coerce), which bounded the class to those two.
  - **SPEC §4.2 states the identifier grammar, and a test pins it to the code.** The first draft of §4.2 said an identifier was "whatever string the host tracker uses to name an issue" while the implementation admitted a bounded class — a contradiction inside this change, and one a specification cannot ship: two conforming readers would disagree about `" a b "`, and a conforming writer could emit a block its own reader cannot parse. The class is now normative (`A-Z a-z 0-9 . _ -`, opening on a letter or digit), with the three mechanisms that bound it — the writer's quoted rendering, the `#` and `/` separators, and whitespace — stated as the reasons. §4.2 also carries an accept/reject conformance table that `@issuegraph/core`'s suite reads and asserts `isRefId` against, so the prose and the predicate cannot drift; widening the class is now explicitly a spec revision rather than an implementation choice, and an unmodelled identifier fails LOUDLY on both sides (a reader diagnostic, a writer throw) rather than filing a graph that lies.
  - **A reference is read LEXICALLY, so YAML cannot retype it.** The reader took a reference from the *materialized* scalar, and YAML implicitly types a plain one — so `1e5`, `0x1F` and `007` arrived as `100000`, `31` and `7`. The first two are valid identifiers under §4.2, so an author on such a tracker had the edge silently pointed at a **different issue**; and if that substituted target happened to be closed, the issue read READY while its real blocker was open — shipping work in the wrong order, which is the one outcome this format exists to prevent. `007` additionally bypassed the canonical-number rejection §4.2's own conformance table requires. A plain scalar's identifier is now its **source text** and a quoted one's its unescaped value; `priority` and `evidence` keep the materialized value, because those genuinely *are* typed. This also removes an asymmetry previously documented as acceptable — quoted `"007"` was refused while plain `007` silently became `7`; both are refused now.
  - **Block discovery asks the parser which key a block carries, instead of matching one spelling of it.** The line prefilter cannot see a flow-root mapping — `{ issuegraph: { blocked-by: [ "#1" ] } }`, which is simply what a YAML serializer emits in flow style — so a conforming third-party writer's block was reported as **no block at all**, `data: null` with zero diagnostics and every edge silently gone. The escape-encoded and explicit-key spellings failed identically. Widening the *pattern* would have been a denylist of spellings that grows a row per review round, with every missing row another silent loss; asking the parser is total by construction. The prefilter is still OR-ed in rather than replaced, because a block that carries the key but does **not** parse must still be selected so the reader can report why — judged by the parse alone it would become invisible. Both halves are neuter-verified as load-bearing. SPEC §4.1 now states the asymmetry: readers take the key their parser reports, writers must write it literally so a tracker mirror can prefilter candidate bodies at all.
  - **`spliceGeneratedEdges` throws rather than silently losing fields it cannot edit.** Now that a flow-root block *reads*, a section that reads fine but cannot be edited line-by-line reached the same `null` return as "there is no block" — and `null` is the caller's signal to prepend, which under §4.1's first-block rule demotes the original block and drops every field the call did not own. Measured on `{issuegraph: {blocked-by: ["#1"], priority: 1, together-with: "#5"}}`: `priority` and `together-with` gone, zero diagnostics on either side. It now fails loudly, which is this package's own stated writer discipline. The throw fires **only when something would actually be lost** — an empty section, an unparseable block, and a body with no block all still return `null`. Giving callers a value to branch on instead of an exception is [#27](https://github.com/autnmy/issuegraph/issues/27).
  - **A projection never testifies that content is absent.** One class, found at two sites in the same review round, and removed rather than patched twice. (a) `blockCarriesKey` read a FAILED parse as "this block has no key", so a malformed flow-root block came back as **no block at all** — `data: null`, zero diagnostics, `isUnreadDeclaration` false — while the block-style spelling of the identical fault reported itself correctly. A failed parse cannot testify to absence; it now falls back to an unanchored key mention, which decides only whether to SELECT the block so the reader can say *why* it is unreadable. (b) `locateSection` returned `null` both for "no readable section" and for "a section I cannot edit line by line", and a caller's response to the first — prepend a fresh block — silently demotes the second under §4.1's first-block rule. It now reports `lineEditable` separately and lists the section's entries **recognised or not**, so the writer counts an author's extension field instead of the recognised-`Frontmatter` projection that omits it by design.
  - **The splice's positive control is comparative rather than a shape test.** It asked only about the RESULT — `data === null` **with** a diagnostic — so a splice that wrecked a block badly enough to make it undiscoverable produced `data: null` with **no** diagnostic (absence is silent by design) and slipped straight through: the caller was handed a non-null body and told it had succeeded, while the requested edge was unwritten and the existing fields were gone. It now compares against the body it started from — a readable declaration that stops being readable is a failed write, whatever the wreckage looks like. Intent is threaded rather than inferred, so the legitimate whole-block removal still succeeds.
  - **An empty section takes its child indent from the header.** The fallback assumed column 2, which is the header's OWN column when the block itself is indented — so a writer's first insert landed as a **sibling** of `issuegraph:` rather than a child. The body still parsed, so the post-edit readability check passed and the caller was told the write succeeded while the blocker it asked for was never readable. Silent under-blocking: the issue reads unblocked when the writer meant to block it.
  - **Behaviour deltas, all in the refusing direction.** A duplicate key — the `issuegraph` key itself, a recognised field, or an unrecognised one — now refuses the block instead of letting the first or last win silently. An empty flow-list entry (`[,]`, `[1,,2]`) refuses the block instead of yielding a partial list. A structurally invalid section refuses rather than dropping one field. One delta goes the other way: an inline flow mapping on the key (`issuegraph: {priority: 1}`) is ordinary YAML and now READS, where the hand-rolled subset refused it.
- **`@issuegraph/cli`: two inputs the libraries cannot use are refused instead of accepted.** Both were deferred from the review of [#26](https://github.com/autnmy/issuegraph/pull/26) with their consequence measured, and both are the same predicate — *a request carries a value the libraries cannot act on, and the CLI takes it anyway*. **Closes [#30](https://github.com/autnmy/issuegraph/issues/30).**
  - **A repository qualifier is asked of `@issuegraph/core`, not accepted as any string.** `asIssue` took any non-null `repo`, so `nodeKey` built a key such as `project#7` that no issue body can reference. Measured: a dependent declaring `blocked-by: project#7` came back HELD, reported as `own issuegraph declaration was not fully read (fail-safe: refusing the node)` — conservative and right, but naming the wrong thing, so a caller could not see that its own input was the defect. `isRepoQualifier` is the predicate the reader's own ref parser calls, so the CLI now asks it rather than restating the grammar or round-tripping the parser. `homeRepo` is held to the same domain for the same reason: it is not a reference, so nothing it accepts can be *mis*-resolved, but it is compared against every node's repo, and an unusable value silently matches nothing and leaves qualified keys where the caller expected bare ones.
  - **Both bounds are enforced at the boundary the two entry points SHARE, not in the JSON validator.** They first landed in `asOrderInput`, which meant `orderFromJson` had them and the exported `deriveOrder` — the same operation, reached directly — did not; a caller holding an `OrderInputDocument` can write `repo: "project"` and `number: 0` and have both type-check, so `nodeKey` rebuilt the unreferenceable `project#7` key anyway. This is the **second instance of the class `duplicateKeyRefusal` already names**, so the fix is the same one: a single `inputDomainRefusal` at `deriveOrder`, covering `repo`, `homeRepo`, `number` and `assigneeCount` together rather than the one field that was reported. Type-checking a field is not checking its domain. The parse-time readers stay — they narrow `unknown` and name the offending path for a JSON caller — and are not a second copy: each rule has one predicate and two callers. The test asserts over the entry-point table, so a third entry point is a row rather than a rediscovery.
  - **A write request naming a field the writer cannot act on is refused at the shared funnel.** `writeRequestRefusal` tested only that the request named *some* field, so `{ serialiseWith: ref }` — one letter off — passed, the writer ignored the property it does not know, and the wrapper returned the **unchanged body at exit 0**: a command telling its caller an edit happened when none did. The allowlist is an argument to `performWrite` rather than one shared list, because `set` owns seven fields and `splice` owns four — a union would wave `togetherWith` through to a splice that ignores it, which is the same defect one field along. Each list is proved to cover its interface **at compile time**, so a field added to `SetFields` or `GeneratedEdges` and not to the matching list fails the build rather than being silently refused or silently accepted. `nothing-requested` now judges values rather than key count, since `{ blockedBy: undefined }` named a key and asked for nothing. TypeScript already refused all of these (TS2561 on a literal, TS2559 through a variable, `exactOptionalPropertyTypes` on the undefined case), so the reachable population is plain-JavaScript callers — for whom a type annotation is a promise to somebody else.
- **`@issuegraph/writer`: the default written block is bare, blank-line-terminated, and auto-links.** `renderFrontmatter`'s `fenceWrapped` now defaults to `false`, refs render as quoted `"#123"` / `"owner/repo#123"`, and the block carries a blank line before its closing `---`. Measured against a live markdown renderer: that form renders as rule / paragraph / rule and auto-links every reference, where the previous fenced bare-integer output rendered neither. Auto-linking stamps a cross-reference on the TARGET issue, which is the only surface anywhere showing what an issue is blocking — §4.3.1 has no `blocks` field. The fenced form is still emitted on request and still parses; existing bodies are not migrated.

Both are pure and total: neither throws on any input, and every anomaly becomes a diagnostic. At 0.1.0 the tokenizer is a hand-rolled restricted-subset reader with no runtime dependencies. That is an internal detail of a surface already pinned by tests, and it is being replaced: the tokenizer moves to an established frontmatter/YAML parser, with the key set exactly what the spec defines ([#6](https://github.com/autnmy/issuegraph/issues/6)). `isUnreadDeclaration` is the question a reader must ask before treating a declaration as complete — a dropped field leaves `data` non-null and looking finished.
- **`@issuegraph/writer` 0.1.0** — the three ways a block gets written. `renderFrontmatter` emits a fresh one; `spliceGeneratedEdges` refreshes only the edges one writer owns and leaves every other byte alone, including author metadata the format makes inert; `backfillFrontmatter` repairs a block a code fence left undelimited by adding the `---` pair its author omitted and changing nothing else. Reading and writing have opposite error disciplines on purpose: a parser takes untrusted issue text and never throws, a writer takes its caller's own data and throws before it can file an issue whose graph lies.
  - **The round-trip is pinned ACROSS the package boundary.** `parseFrontmatter(renderFrontmatter(x))` is asserted against `expectedParseOfRender(x)` from inside the writer's own suite, so a spelling that drifts on either side fails rather than being caught by whichever package happened to own both halves.
  - **Ownership is per-field and opt-in.** An omitted field is untouched — round-tripping parsed values back through a splice would launder away exotic spellings and unparseable items the parser tolerates with a diagnostic, so omission is the honest "not mine" signal. What a PRESENT `null` means is not uniform: on the scheduling edges (`blockedBy`, `serializeWith`) it removes, while on `decomposedFrom` and `duplicateOf` it also leaves the value alone, because the established caller shape there is "write it when the block lacks one, never clobber one that is already there" and such a caller passes `null` to mean exactly that. So those two cannot currently be CLEARED through a splice; the gap is stated rather than closed by overloading a value that already has a caller.
  - **The backfill preserves rather than re-spells.** Re-rendering from the parsed value is lossy by construction — a renderer emits only what the parser models — and it deleted rejected field values, inert extension fields and YAML comments. It also repairs ONE shape: a block inside a code fence the walk can establish. An unfenced key is refused, because a fence is only one of the containers that make a column-zero key prose, and enumerating the rest grows a rule per review round.
- **`@issuegraph/reader` 0.2.0.** Two changes land in the same unreleased version — nothing publishes on a merge, so they share it rather than one of them claiming a version nobody can install.
  - **the line grammar is now shared, and a key-quoting defect is fixed.**
    - `locateBlock`, `topLevelKeyScalar`, `readMappingEntry`, `FENCE_OPEN` and `FENCE_CLOSE` are exported for `@issuegraph/writer`. An editor has to locate the same block, open the same section and recognise the same entries as the parser; spelling those rules twice is how a write hands back a body its own parser cannot read.
    - **Fixes [#10](https://github.com/autnmy/issuegraph/issues/10).** `readMappingEntry` toggled quote state anywhere on the line, so a stray apostrophe in an ORDINARY key — `note's: x` — swallowed the colon and the line read as unparseable. An unparseable child is structural, so the whole block degraded and every real edge beside it was lost, over a field §4.1 says has no power at all. A quoted key must OPEN with its quote; anywhere else a quote is plain content. Escaped quotes (`''`, `\"`) are now tracked, so `'owner''s-note'` is one key.
    - The parse walk opens its section through `topLevelKeyScalar` rather than a second spelling of the same rule, so the predicate a writer locates a section by is the one the walk uses.
  - **`buildModel` gains an under-read tier.** `NodeInput` carries a **required** `declarationRead: 'read' | 'under-read'`, and the model acts on it: an under-read node is refused, so is any node sharing its `serialize-with` component (a dropped `serialize-with` means the component's true extent is unknown), and so is a node whose edge resolved to a CLOSED node that had itself been under-read — `blocked-by` and `together-with` both read the target's `open` flag to DISCHARGE the edge, and `targetKey` resolves that ref through the target's `duplicate-of`, so a dropped one reads the flag off the wrong node (a closed duplicate rather than a still-open canonical). `serialize-with` needs no such guard: it unions whatever the state, so closure discharges nothing there. Both shapes raise a diagnostic. `Model.underReadKeys` exposes the under-read set structurally, because one case is provably not the reader's to close: when the DROPPED FIELD IS ITSELF AN EDGE the peer's identity is what the parse destroyed, so the only sound refusal would be a global stall — that policy is the host's, and this is the seam for it. The package already shipped `isUnreadDeclaration` and a README insisting the question be asked — and then `buildModel` never asked it, so `blocked-by: [123, not-a-ref]` admitted a candidate gated on `#123` alone and `serialize-with: not-a-ref` admitted one that read exactly like a body declaring no relation. `data` alone cannot carry the answer, which is why the field is required rather than optional: an omission would compile. Effective priority is deliberately untouched — an under-read node under-reports a blocker's urgency, which reorders work but never admits any. **Breaking:** every producer must supply the field.
- **`@issuegraph/store` 0.1.0** — a client store for a document plus the data-source adapter port, so a host supplies its own tracker (BYO-DataSource) and the package fetches, authenticates and persists nothing.
  - **The order can be trusted.** Edits render optimistically; the selection order derives from **landed** edges alone, so an unlanded edit cannot move a ranking. While a write is in flight the order reports itself `held` and the previous rows stand.
  - **One authoritative operation at a time.** `hydrate` and an `applied` or `unchanged` `dispatch` all answer with a whole document, and the store runs one at a time — two unversioned snapshots in flight cannot be ordered, and the later answer arriving first silently rolls an edge back out.
  - **A failed write is marked, never reverted.** `failed` and `conflict` states; nothing auto-merges, auto-reverts or times out. A conflict's `upstream` is kept for view-diff and never adopted, so `discardMine` drops the overlay and `retry` re-dispatches; "retry on latest" is a host composition of `rehydrate()` + `retry()`, because the decisions across that await are about user intent.
  - **Refusals never reach the adapter.** Structural ones the store makes itself; graph-shaped ones come from an injected `EdgeGuard`. An injected deriver supplies the order — the store owns *when* it is recomputed, never *what* it is.
  - **A host cannot corrupt it by accident.** Every array reachable from a snapshot is frozen, copied first so an adapter is never frozen out of its own storage; every reused slice is compared structurally rather than field by field; and a deriver, guard or subscriber that throws cannot break the store or strand the queue.
  - **Two reference adapters.** An in-memory one a demo runs on with no backend at all, and a scripted asynchronous one that settles only when told to, so every failure arm can be induced rather than asserted.
- **`@issuegraph/viewer` 0.1.0** — the layer-1 viewer: `{issues, edges, order}` plus a projection choice in, `onSelect`/`onHover` out, and nothing else. Three projections over one document — `linear` (the order as rows, complete at any size), `graph` (the spine with gutters and edge arcs) and `tree` (the `decomposed-from` hierarchy). Framework-free, no CSS import and one runtime dependency, so the built entry imports on the declared Node floor with no DOM present.
  - **Rendering is pure; the DOM is a shell.** A projection returns an element-spec tree, one serializer renders it to markup and one walk builds it as nodes — so a test on the string is evidence about the nodes, and the whole grammar, layout and key map is testable on a runtime with no DOM.
  - **Every colour, type and spacing value is a custom property, and geometry is theme data.** Rendering one document under two themes produces BYTE-IDENTICAL markup and different styles, which is the assertion that makes "themeable" a fact rather than a claim about the existence of some variables. The shipped dark palette is the DEFAULT theme, not the styling.
  - **The five relationships are separable on four channels** — dash, terminal marker, glyph, hue — asserted with hue removed entirely, and declared as a total mapping over the format's own field list so a sixth relationship fails the build rather than rendering untreated.
  - **Held work keeps its position.** A graph-derived hold renders inline at the rank the work would have taken with `—` for the rank; a runner- or tracker-derived hold earns no rank slot and collapses into a footer with duplicates. The two families never share a treatment.
  - **The graph refuses rather than degrades** — component capsules past 60 nodes, clusters only past 300, each naming the next move.
  - **`navigate` is a pure reducer over the scene's PUBLISHED order**, which on the spine is rank order and never geometry, so keyboard traversal cannot drift toward the picture.
  - **A deep link is checked rather than escaped, and canonicalized first.** `url` is the one input field that becomes an executable surface, so only `http:`/`https:`/`mailto:` and relative values are linked and anything else is dropped with a diagnostic. The value is canonicalized the way a URL parser does — every ASCII tab and newline removed from ANYWHERE in it, then leading controls stripped — before the scheme is read, because `java<TAB>script:` reaches a browser as `javascript:` while a raw scan finds no scheme at all and reads it as relative. Rows use plain list semantics with `aria-current` rather than `role="option"`/`role="treeitem"`, both of which forbid the focusable deep-link chip every row carries.
  - **One rule decides where focus sits**, shared by every projection and by `reconcile`, so the element carrying `tabindex="0"` and the state a host reads cannot disagree — a requested key a projection no longer draws used to render no tab stop at all, leaving the viewer unenterable from the keyboard. A scene publishes `navigable` beside `focusOrder` because a gutter node is reachable sideways without being a position in the order, and every key either names is focusable exactly once.
  - **Every traversal is iterative, and both renderers are.** The tree projection's nesting is the host's `decomposed-from` chain and nothing bounds it, so a recursive walk turns a valid document into a `RangeError` out of a function documented as TOTAL. The cluster walk, the tree's order and element builds, `renderMarkup` and `materialize` are all explicit-stack, exercised at 20,000 levels — the class is removed rather than the input capped, which would have invented a depth budget the design does not have.
  - **What a scene publishes as a navigation target is DERIVED from what it draws**, not declared beside it. Three review rounds found the same defect in three places — a gutter node with no `tabindex`, a refusal replacing the whole canvas while its keys stayed published, an enclosure sharing a key with the node it decorates and winning the mount index. Filtering the published sets by what renders makes "every published target is focusable exactly once" hold by construction, and one test asserts it across every projection for the fixture, a held together unit, both refusal modes and an empty document. The lateral axis is recorded from both ends, so the documented path from the spine and back goes both ways.
  - **The refusal offers an action a host can perform.** "Select one component to draw it" named something nothing in the package could do — the capsules carried no identity, nothing dispatched from them, and the viewer never narrows to a component. Each capsule now carries its component's lead as a pointer identity and the instruction says what actually happens next: the host narrows the document, because narrowing is the host's job in a package that renders exactly what it is given.
  - **`decomposed-from` cardinality is applied where the edges are read.** A missing first origin and a resolving second were recorded independently, so the tree nested an issue under one parent while printing that it came from another — two contradictory claims about one single-cardinality field. First declared wins, whether or not it resolves, and the projection's own unreachable check is gone rather than left guarding nothing.
  - **The canvas reserves the margin an enclosure needs, and a same-column edge faces its channel.** A `together-with` unit on the first or last row drew outside the viewBox and was clipped; and "face the other node" says nothing about two nodes sharing a column, where defaulting left was correct for the spine only by coincidence — for two left-gutter nodes the channel is on their right, so both endpoints left the canvas and the path crossed the boxes.
  - **The rail is positioned FROM the layout, on the canvas it describes.** Emitted as a sibling block, the ranks and readiness stations rendered above the drawing, so the reader had to hold the correspondence in their head — the opposite of the design's claim that the spine IS the order. Both now share one stage sized in the layout's own units, and a spine node is labelled once, by its rail row, rather than twice. Layout output rides declared `--ig-row-*`/`--ig-stage-*` custom properties, kept disjoint from the theme tokens so the stylesheet guard can still fail on a `var()` nothing sets.
  - **A nested control keeps its own keyboard, and the canvas is a group.** `keydown` bubbles, so the viewer's Enter handling was suppressing the deep links every projection deliberately exposes; activation on a self-activating element is now that element's, while movement keys stay the viewer's. And `role="img"` on the SVG flattened every descendant into a single image node, hiding the roles and labels that make gutter and held nodes reachable — a container of separately focusable children is a group.
  - **Focus and pointer are two identities.** Every focusable element carries `data-ig-key` and exactly one element per key does, so `focus()` cannot land on the wrong one; decoration painted behind the nodes carries `data-ig-group` and stays out of that index while `mountViewer` still resolves a pointer on it — the design states the `together-with` connector IS a click target.
  - **Every published lateral pair is reversible.** A node has one neighbour per side, so a gutter node shared by two spine slots cannot point back to both; only a pair whose reverse is still free is published, and the invariant is asserted over the whole map rather than for one example.
  - **One issue holds one place in the order.** A hand-built document naming the same issue in two slots — or in a slot AND in `excluded`, or twice in `excluded` — published the key twice, so `ArrowDown` from the first occurrence resolved to the same key, answered `none`, and stranded everything after it.
  - **Purity is measured, not promised:** a scan over the shipped sources carries a positive control that plants every forbidden API and requires the detector to report all of them, and every module is imported with the browser globals removed.
- **`@issuegraph/derive` 0.1.0** — the selection order, one layer above the reader. `deriveIssueOrder` returns ranked slots, held slots carrying `rank: null` and the reasons they are held, together units collapsed to one slot, excluded duplicates, and priority promotions in the spec's own `P3 -> 0` notation; `wouldCycleOnBlockedBy` refuses a `blocked-by` edge that would close a cycle, synchronously and from data already in hand.
  - **The host's ranking is an input.** Whatever already orders a backlog — mapped labels, issue types, saved queries — is supplied, never re-derived, so the package does not become a second ordering engine beside the authoritative one. Frontmatter modifies that ranking rather than replacing it, which is what makes the package useful at zero adoption.
  - **These are the two ports `@issuegraph/store` declares and does not implement** — `OrderDeriver` and `EdgeGuard`. The store owns *when* the order is recomputed; this owns *what* it is.
  - **A held slot keeps its position.** "Why isn't my P1 running" is answerable at the rank the work would have taken; a claim-time selector that drops held work deletes exactly that information.
  - **Purity is pinned mechanically, not asserted.** The tests read the modules' own syntax tree for a dependency outside a four-entry allowlist and for module-scope mutable state, and pin reference identity and freshness so a memo returning the stored model fails — which a compare-by-value test alone would let through.
  - **Pinned against the reference prototype's own seed**, before and after its demonstration edit, so the two cannot drift.
  - **Duplicates resolve the model's way, and the two sites diverge on purpose.** An edge naming a duplicate names its canonical (§4.3.3), so both the cycle walk and the promotion provenance follow it — through `Model.duplicateCanonical`, never a second duplicate-chain walk. Where they differ: the cycle guard KEEPS an edge declared by a duplicate, because dropping one removes reachability and a cleared `duplicate-of` brings it back with the cycle already written; the provenance drops it, because an edge the model never read cannot be the reason it gives for a promotion.
  - **Both propagation paths, and both endpoint spellings.** Effective priority relaxes along `together-with` as well as `blocked-by` (§6.3), so promotion provenance reads both — a P3 grouped with a P0 is promoted and must say through whom, and the together half names the ADJACENT peer rather than the component (relaxation flattens a component to one priority, so enumerating it makes every member read as a cause). And the cycle probe resolves its own two arguments, not just the stored edges: each is walked under the key as given AND its canonical, because resolving only the stored side leaves the arguments in a different key space (a self-dependency goes unseen), while replacing the raw spelling would remove refusals a duplicate's own kept edges still earn.
  - **A slot's sizes describe the whole slot.** A together unit's serialize footprint is the union over its members' components, not the lead's — every member has to be free before the unit is admitted. Reading the lead alone made a structural number depend on the base ranking, since which member leads is a ranking outcome, so two clients ranking differently reported different sizes for one graph.
- **The in-memory demo (`demo/`).** A live backlog running on a data source that holds one document in a variable — no tracker, no app installation, no auth, no backend — which is what makes BYO-DataSource a fact rather than a claim: a seam only ever driven by one real adapter is a seam by assertion. It loads the packages in the browser from the `exports` entries their manifests declare, through an import map, so there is nothing between the published package and the page. Every edge type, both hold families, all three readiness stations, all three rank-provenance forms and all five edge states are reachable without editing anything first, and that coverage claim is a test rather than a sentence, because a seed drifts. `failed` and `conflict` are induced from the page itself by arming what the tracker answers next. It is a **consumer**, not a package: `private: true`, and outside `packages/` on purpose, since that directory is what the isolation guard, the consumer smoke test and the lint config all read as "this ships".
  - **The order comes from `@issuegraph/derive`, not from the demo.** The store takes its deriver as a port with no default, so a host must supply one — and this host supplies the published derivation rather than a second reading of §6.2, §6.3 and §6.4. What is left on the demo's side is a PROJECTION: the store's document onto the derivation's node input, and the derivation's slots onto the stations the page draws. What stays host-side stays because the specification puts it there — the executor holds (§6.8: hold semantics are never encoded as format fields) and the concurrency cap (§6.5: dispatch policy is out of scope). Those are inputs to a derivation, not a derivation.
  - **Two defects the swap surfaced, both in the demo.** §6.7 names `blocked-by` and `serialize-with`; the demo had generalized it across both GROUP fields, drawing an unresolvable `together-with` as a non-blocking note while the reader refuses the declarer (§4.3.7 — a unit cannot be claimed atomically around a member it cannot identify), which rendered a held row with no reason on it. And a slot's serialize footprint includes its own members, so a together unit of two with no `serialize-with` edge reads 2 — tested against 1, that drew "serialized, group of 2" on a pair nothing serializes. Both were found by the test that pins every hold chip against `IssueOrderSlot.ready` in both directions, which is the point of keeping the chips as presentation over a verdict the package owns. A third, from the review: the relationships panel offered `delete` on every edge, including one that exists only as an optimistic overlay — and the store validates every non-create mutation against the LANDED document, so a click stacked an `invalid` state and a second `discard mine` onto a row that was already `failed`, and moved nothing. The control is now asked through the store's own `findEdge`, so the page cannot offer what the validator refuses — and not while an edit is in flight either, since a pending DELETE keeps its edge in `landed` until it settles and the landed answer is stale for that whole window. A fourth: the host reported `assigneeCount` for the exact ref an executor named, while §4.3.7 makes a together unit ONE atomic claim — so a third issue serialized against an unnamed member of a claimed unit read as ready. Active claims are now expanded across their together components before the projection, and the chips read the same expanded set the model was given. And a fifth, from the accessibility layer: each relationship row was itself the `role="button"`, which makes its descendants PRESENTATIONAL — so the row's own actions sat inside a control that flattens them, and the row had no accessible NAME. Read out of the browser's accessibility tree, every row came back as an unnamed `button` containing a `delete`. Selection is now a real `<button>` carrying the edge's identity with the actions as its siblings, which also deleted the two hand-written key listeners and the target guards the nesting had made necessary.
  - **One divergence is pinned, not patched.** The old deriver contracted a `together-with` unit to a single vertex before searching for cycles and the published one does not, so a `blocked-by` cycle running THROUGH a unit is no longer refused — and it is a real deadlock `Model.cycles` reports nowhere. Re-adding contraction would rebuild the second reading this removes and disagree with every other consumer, so the demo adopts the package's answer, a test pins the gap with a control, and the finding is filed against the package as [#43](https://github.com/autnmy/issuegraph/issues/43).
- **`@issuegraph/core`: `SYMMETRIC_EDGE_FIELDS` and `isSymmetricEdgeField`.** Which relationship kinds carry no direction (§4.3.4, §4.3.7) is format vocabulary, so it belongs with the rest of it rather than being rediscovered by each consumer that has to compare two edges.
- **`pnpm run ci` builds before it typechecks.** A package consuming another's published types cannot be typechecked until that one has emitted them, so on a fresh checkout the old order failed before it reached the build. Ordering it correctly is what makes a multi-package workspace check at all.
- **Import linting.** ESLint over `packages/` with `no-restricted-imports`, `import-x/no-absolute-path` and `import-x/no-relative-packages`. A real parser rather than a pattern, so template literals and comments are handled by construction. Each rule has a deliberate-violation test, and a control asserting the config matches the file.
- **Isolation guard.** `pnpm run check:isolation` refuses a forbidden dependency — by key, `npm:` alias target, or git URL — a relative import escaping its own package, and a consumer's brand token in any text a package ships, `package.json` metadata included. It scans by content rather than by an extension list, and does not exempt built output, because what a package can publish is an open set. Proved by tests that break each rule deliberately.
- **Version consistency.** SPEC.md §8 and the README both still said `v0.1.0` while the spec's own version header and this changelog said `0.2.0`. Corrected, and pinned by a test so the header and §8 cannot drift apart again.

## 0.2.0 — 2026-08-15

- §6.4 selection tiebreak: **newest first** is the default (was oldest first), with rationale — starvation avoidance now belongs to effective priority (an old issue that matters inherits urgency from its dependents), while recency buys premise freshness against issue-body rot. ## 0.1.0 — 2026-08-14

Initial draft.

- Carrier: standard YAML **frontmatter** on the issue body (`---`-delimited, top of body, never hidden), namespaced under a top-level `issuegraph` key. Nothing bespoke: the universal convention, on purpose.
- Fields: `blocked-by`, `decomposed-from`, `duplicate-of`, `serialize-with`, `together-with`, `priority`, `evidence`.
- No container issues: `decomposed-from` is provenance; tracking issues are replaced by queries; whole-feature gates are ordinary issues blocked by their siblings.
- `serialize-with` groups (connected components, width-1 semaphore, claim-time direction) and `together-with` units (group readiness over boundary-crossing edges, atomic claim, max effective priority, individual closure). The coordination vocabulary is closed at these two; preference fields are rejected.
- Scalar carrier precedence: established tracker conventions (priority labels, an evidence label pair) are canonical over the frontmatter; relationship fields are frontmatter-canonical.
- Writing rules bind every writer; the size rule; closure semantics (any closure unblocks, non-completed closure flags dependents for re-groom); the decision-issue pattern for nameable human gates; holds as executor policy composed via ready-and-eligible selection.
- Reading rules: ready set, backward-flowing effective priority, oldest-first tiebreak, detect-on-read cycles, fail-safe unresolvable references.
- Scope rule: the format describes work, never execution.
